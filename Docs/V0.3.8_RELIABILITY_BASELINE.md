## 4. 已确认缺陷（Confirmed）

以下问题均已通过阅读源码定位到具体行号，或已由既有代码逻辑直接证实。

### C-01 · P0 · 恢复接口存在路径穿越，备份目录可被越界读写

**位置**：`src-tauri/src/commands/sync_cmd.rs:156-174` → `src-tauri/src/sync/restore.rs:26`

`webdav_restore_backup` 把前端传入的 `filename` 原样拼进远端路径：

```rust
// restore.rs:26
let remote_backup_path = format!("{}/{}", clean_dir, backup_filename);
```

而 `WebDavClient::build_url`（`src-tauri/src/sync/webdav.rs:30-37`）只做字符串拼接，
不做任何规范化或穿越检查：

```rust
fn build_url(&self, remote_path: &str) -> String {
    let clean_path = remote_path.trim_start_matches('/');   // 只去前导斜杠
    ...
    format!("{}/{}", self.base_url, clean_path)
}
```

`remote_path` 中的 `../` 会原样进入 URL，由 reqwest / 服务端解析成父目录。

**影响**：传入 `filename = "../../任意目录/backup_x.db.gz"` 即可让恢复流程从
`remote_dir` **之外的目录下载并解压一个文件**。结合下一条（恢复内容未预检），
攻击面覆盖整个 WebDAV 账号可读范围。同时 `list_files` 也会把越界文件列入候选
（`webdav.rs:329` 只按 `.db.gz` 后缀过滤）。

**严重程度**：高。触发需要恶意/被篡改的前端或 XSS（CSP 已收紧，实际利用难度较高），
但这是恢复路径上「本应最保守」的入口缺少最基本的输入校验。

**复现**：调用 `webdav_restore_backup("../../../etc/backup_evil.db.gz")`，
观察最终请求 URL 是否仍以 `base_url + remote_dir/` 开头。

### C-02 · P0 · 恢复前无任何预检，损坏备份会直接覆盖可用数据库

**位置**：`src-tauri/src/sync/restore.rs:76-123`

恢复流程是：下载 → gunzip 到内存 → 写临时文件 → **直接用 SQLite Backup API 覆盖目标库**。
中间只有一处校验：

```rust
// restore.rs:97-111 —— 唯一的前置校验
let restored_version: i64 = src_conn.query_row(
    "SELECT COALESCE(MAX(version), 0) FROM schema_version", [], |row| row.get(0)
).unwrap_or(0);

if restored_version > crate::db::BASELINE_VERSION { /* 拒绝高版本 */ }
```

缺失的预检项（任务书 P0-1 任务 C 逐条对照）：

| 应有检查 | 现状 |
|---|---|
| gzip 是否截断/损坏 | `read_to_end` 只在读取阶段报错；**部分损坏 + 恰好能解压**时无检测 |
| 数据库完整性 | 无 `PRAGMA integrity_check` |
| 备份是否为有效 SQLite | 无；任意字节流只要能解压就会尝试当库打开 |
| 实体数量合理性 | 无（0 章节 / 0 卷的合法备份与「备份损坏」无法区分） |
| 资产引用与文件一致性 | **恢复完成后才扫描**（`restore.rs:150-237`），此时覆盖已发生 |
| 目标磁盘空间 | 无 |
| 备份清单 / 校验和 | **备份格式里根本没有清单** |

**特别注意 `unwrap_or(0)`**：损坏或非 SQLite 文件读不到 `schema_version` 时会被当成
`version = 0`，顺利通过版本检查，然后进入 `Backup::run_to_completion` 覆盖流程。
这是「无法识别的数据被当作合法备份处理」的直接违反。

**严重程度**：高。一次失败的中断上传或被截断的下载，就可能把用户当前可用的库覆盖成空库或半库。
好在 `restore.rs:28-49` 确实先做了本地 `pre_restore_*.db` 快照（**这是当前唯一的保护**，
且该快照仅存在于本地、恢复失败路径下不告知用户）。

### C-03 · P0 · 备份轮转在新备份未验证前就可能删除旧备份

**位置**：`src-tauri/src/sync/backup.rs:109-117`

```rust
// 7. Prune old backups (keep latest 20)
if let Ok(backups) = client.list_files(&clean_dir).await {
    if backups.len() > 20 {
        for old_backup in &backups[20..] {
            let old_path = format!("{}/{}", clean_dir, old_backup.filename);
            let _ = client.delete_file(&old_path).await;   // 失败静默
        }
    }
}
```

三个问题：

1. **轮转只看数量，不看新备份是否可信**。上一步的 `move_file` 成功即认为新备份落盘，
   但远端文件内容从未被回读校验过（`get_file_size` 校验在 `backup.rs:88-97`，
   且被 `if let Ok(...)` 包住——**服务端不支持 HEAD 时整段校验被跳过**）。
2. **排序不可靠**。`webdav.rs:346` 用 `b.filename.cmp(&a.filename)` 排序，
   依赖文件名里的时间戳格式；一旦有非 `backup_` 前缀的 `.db.gz` 文件，
   或用户手动放了别的文件，`&backups[20..]` 会删掉**任意**排在后面的文件。
3. **删除失败完全静默**（`let _ =`），轮转数量只减不增，且用户无从得知。

**严重程度**：中高。与 C-02 叠加时，风险是「唯一一份好的旧备份被删 + 新备份不可用」。

### C-04 · P0 · 备份中途失败会残留 `.tmp` 半成品，且被轮转列表当作正式备份

**位置**：`src-tauri/src/sync/backup.rs:76-104`

上传采用 `.tmp` + `MOVE` 的两段式，设计意图正确。但在
`client.move_file()` 返回 `Err` 时（第 100 行），清理是 `let _ = client.delete_file(...)`
—— **忽略删除失败**。若此时进程被杀或网络再次中断，`.tmp` 文件永久留在远端。

而 `webdav.rs:329` 列举文件时**只按 `.db.gz` 后缀过滤**，
`backup_20260101_000000Z.db.gz.tmp` 的后缀是 `.tmp`，因此**不会**被误列。

**修正**：C-04 的实际危害比初判小（后缀过滤挡住了误列）。真正的问题是 `.tmp` 残留**永不清理**，
远端目录会随着每次失败累积垃圾文件。风险等级下调为中。

### C-05 · P0 · 回收站批量删除无事务，中途失败留下半删除状态

**位置**：`src-tauri/src/db/trash.rs:178-202`（`purge_trash_item`）、
`src-tauri/src/db/trash.rs:204-226`（`empty_trash`）

```rust
// trash.rs:204 empty_trash —— 5 条 DELETE 顺序执行，无事务
pub fn empty_trash(conn: &Connection, novel_id: &str) -> Result<()> {
    conn.execute("DELETE FROM chapter WHERE novel_id = ?1 AND deleted_at IS NOT NULL", ...)?;
    conn.execute("DELETE FROM volume ...", ...)?;
    conn.execute("DELETE FROM worldview_entry ...", ...)?;
    conn.execute("DELETE FROM character ...", ...)?;
    conn.execute("DELETE FROM plot_item ...", ...)?;
    Ok(())
}
```

`purge_trash_item` 的 `"volume"` 分支同样是两条 DELETE（`trash.rs:184-185`）。

两条 DELETE 之间若发生错误（磁盘满、库被锁），前一条已提交、后一条未执行，
结果是一个**部分清空且无法回滚**的状态：章节没了但卷还在，或设定没了但人物还在。
这直接违反任务书 7.2 的「删除失败时，界面不能假装删除成功」——函数确实返回了 `Err`，
但**数据已经被改了一半**，用户重试或继续操作会面对不一致的库。

**严重程度**：中高。触发需要并发/资源故障，但这类故障正是可靠性专项要覆盖的场景。

### C-06 · P0 · AI 提炼全链路失败会被伪装为「未发现新设定」

**位置**：`src-tauri/src/agent/extraction.rs:730-733` 与 `:758`

### C-09 · P1 · EPUB 导入无解压体积与文件数上限

**位置**：`src-tauri/src/import/epub.rs:212` 起，`commands/mod.rs:708-717`

```rust
// epub.rs:241 —— 遍历全部条目，无数量上限
for i in 0..archive.len() {
    if let Ok(f) = archive.by_index(i) { ... }
}
```

`parse_import_epub` 接收前端传来的 base64 全文并整体解码到内存
（`commands/mod.rs:712-716`），随后对 zip 内每个条目执行
`read_to_string`（`:268, :394, :417, :454, :528` 等）**无上限**。

**影响**：构造一个压缩后极小、解压后数 GB 的 EPUB（或数万个小文件），
即可让应用在解析阶段耗尽内存。仓库依赖的是 `zip = "9.0.4"`，
`ZipArchive::by_index` 本身不解压，只有 `read_to_*` 会，所以这是**解压炸弹**而非
「打开即膨胀」，但仍足以打爆内存。

`tests/epub_import.rs` 现有 3 个测试均为正常路径用例，**无任何恶意输入测试**。

### C-10 · P1 · `open_external_url` 未限制目标 host

**位置**：`src-tauri/src/commands/update_cmd.rs:157-189`

```rust
if !trimmed.starts_with("http://") && !trimmed.starts_with("https://") {
    return Err("仅支持打开 http/https 协议的链接".to_string());
}
// macOS: Command::new("open").arg(trimmed)
```

只校验协议前缀。传入 `http://169.254.169.254/latest/meta-data/`（云元数据服务）
或任意内网地址即可让系统浏览器访问内网资源（SSRF 变体 / 本地网络探测）。

值得肯定的是：`ai/gateway.rs:304-334` 对模型 `base_url` 做了严格的明文 HTTP 拦截
（仅允许 localhost / 127.0.0.1 / 0.0.0.0 / 私有网段），并有 6 条单元测试覆盖。
**外链接口没有同等约束，属于策略不一致。**

---

### C-11 · P1 · 恢复后图片写入前未校验引用有效性，且非原子

**位置**：`src-tauri/src/sync/restore.rs:191-224`

这一段实际上是本仓库**做得最好的地方**：它按 SHA-256 校验远端图片内容
（`restore.rs:211-222`），哈希不符时拒绝写入并记入 `issues`。
旧实现丢弃 hash 的问题已被修复。

但仍有两点：
- `fs::write` 覆盖本地同名文件时**没有先写临时文件再 rename**，
  中途失败会留下被截断的图片文件（`:223`）。
- `issues` 只在**全部恢复完成后**返回；数据库覆盖早已发生（第 115-120 行）。

## 7. 建议修改范围与兼容性影响

| 阶段 | 建议动作 | 兼容性影响 |
|---|---|---|
| P0-1 | 为备份引入版本化清单（sidecar `.json`），恢复时按「有清单走校验、无清单走兼容分支」处理 | **旧备份完全兼容**（无清单时不拒绝）。不改 `backup_*.db.gz` 本身格式 |
| P0-1 | 在 `webdav_restore_backup` 入口加文件名白名单校验 | 无破坏性；仅拒绝含 `/`、`\`、`..` 的输入 |
| P0-1 | 恢复前加预检（`PRAGMA integrity_check` + 实体计数 + 格式识别） | 预检失败**拒绝恢复**，不静默跳过 |
| P0-1 | 轮转改为「仅在新备份通过校验后执行」，删除失败上报 | 行为变更：轮转次数可能少于 20 |
| P0-2 | `empty_trash` / `purge_trash_item` 包进事务 | 纯加固，签名不变，行为在成功时完全一致 |
| P0-3 | 新增版本一致性脚本 + CI job；release 前校验 tag == 配置版本 | 发布被门禁；不影响开发 |
| P1-2 | 让 `run_parallel_extraction` 返回结构化结果（成功/部分/失败+错误分类） | **需同步改前端展示**，是本次唯一触及前端的 P1 改动 |
| P1-3 | 收紧解析失败日志（去掉正文片段）；外链加 host 限制 | 日志内容变化；外链可能拦截极少数非常规 URL |
| P1-4 | EPUB 加条目数 / 解压体积上限 | 超限文件被拒绝，需在错误信息中说明原因 |

**明确不做**：不重写迁移体系（已够用）、不改前端编辑器、不换数据库、
不改备份文件名格式、不引入新的任务队列。
