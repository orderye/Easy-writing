- `src-tauri/src/sync/webdav.rs`

## 3. 本轮新发现的缺陷（不在任务书内）

这四条都是**测试真实跑出来的**，不是代码审查推断：

1. **轮转从不删除清单 sidecar** —— `list_files` 只返回 `.db.gz`，sidecar 从不出现在轮转候选里。每删一份旧备份就在用户 WebDAV 上留一份孤儿 `.json`，且没有任何后续机制会清理它。已修复：`prune_remote_backups` 删除备份时一并 `delete_file("<path>.json")`（404 视为成功，历史无清单备份不受影响）。
2. **`restore_from_snapshot` 可能把回滚变成数据销毁** —— `Connection::open` 对不存在的文件会**新建一个空库**，随后 Backup API 会用这个空库覆盖目标库。即「快照丢失」→「数据被清空」。已修复：回滚前显式检查文件存在，并复用 `preflight_backup()` 验证快照可用。
3. **`z-60` 在 Tailwind v3 下不生成任何 CSS** —— 默认 z 轴刻度只到 50。仓库里有 **4 处**破坏性操作确认弹窗（`asset_gallery.rs:806/860`、`novel_manager.rs:688/755`）写着 `z-60`，类名在、样式为空，弹窗拿不到预期层级。已改为任意值写法 `z-[60]`（实测生成 `.z-\[60\]{z-index:60}`），并加全仓护栏 `every_z_index_class_in_frontend_actually_generates_css`。
4. **备份完整性缺口被 IPC 边界吞掉** —— 后端已有 `verified` / `manifest_uploaded` / `image_upload_failures`，但 `webdav_backup_now` 只回传文件名，作者永远只看到「✓ 备份成功」。已改为返回 `BackupReport`。

另记录一项**瞬时故障**：`bundle_dmg.sh` 首次构建失败、无代码改动重跑即成功，且失败会遗留挂载卷与 46 MB 的 `rw.*.dmg`。已加 `scripts/tauri-build-retry.sh`（见 §8）。

### 3.5 CI 才暴露的第五个缺陷：我自己写的不稳定测试

这条**本地 3 轮与首轮 CI 都通过，第二次 CI 才失败**：

```text
test empty_overwrite_without_confirmation_changes_nothing ... FAILED
panicked at src-tauri/tests/restore_safety.rs:923:5:
拒绝原因必须明确说明这是空库覆盖，实际：
预检候选备份已失效或被清理，请重新执行预检后再恢复。当前数据库未被改动。
```

根因是我设计的内容寻址候选机制与并行测试相撞。预检候选文件叫
`<sha256(备份包)>.db.gz`，而多个用例发布的是**空库备份**——
schema 相同、数据相同，于是 gz 字节完全相同、token 也相同。
一个用例恢复成功后调用 `remove_candidate(token)` 删掉共享文件，
另一个并行用例紧接着收到「候选已失效」，而不是它要断言的「未确认的空库覆盖」。

这不是生产缺陷（生产上两份字节相同的备份本就该是同一个 token；
同一时刻只有一个用户在操作，且恢复期间按钮被 `is_webdav_syncing` 禁用），
但它是**我的测试引入的真实不稳定因素**，只在 CI 的 CPU 数与调度下现形。

修复：每个用例在备份前写入一条以自身临时目录路径为值的 nonce
（`app_setting.ew_test_nonce`），保证各用例备份内容互不相同、token 互不相同。
`restore_safety.rs::publish_backup` 与 `webdav_integration.rs::seeded_pool`
两处发布入口都加了，并在注释里写明原因，避免以后有人当作冗余删掉。

验证：`--test-threads=4`（贴近 `ubuntu-latest` 的 4 vCPU）连续 5 轮，
`restore_safety` 33 项 + `webdav_integration` 21 项全部通过，0 失败。

值得记下的教训：**只在开发机上跑一遍的并发测试不算验证过**。
本地默认并发度与 runner 不同，这类竞态只有真实 CI 能暴露 ——
而这一整轮里，正是「把东西推到 CI 上跑」这个动作本身提供了本地拿不到的信息。

### 7.1 从代码与 git 历史确认的真实版本

### 7.2 fixture 构造方式的诚实说明

V001 在阶梯引入后被改过，所以「今天跑 V001 得到的库」严格说不等于
「v0.3.4 用户手里的库」。测试采用**先建完整 v3 库、再按历史状态精确退化**
（删掉后续版本才有的表/索引、回退 `schema_version`），好处是表结构直接来自
当前代码，不会因为 fixture 写错列名而测到一个现实中不存在的库；
退化清单在 `V003_INDEXES` / `V002_ONLY_OBJECTS` 中显式列出，可核对。
每个 fixture 建好后都有**前置断言**确认它确实处于目标状态（例如 v2 fixture
必须没有 `idx_asset_hash`），避免用例空跑。

而「V001 变更后历史库缺列」这一真实场景，由原有的
`legacy_database_gets_missing_columns_backfilled` 覆盖（显式手工建缺列表，
并先断言确实缺列）。

### 7.3 失败路径

- `v2_migration_failure_does_not_mark_version_as_applied`：删掉 `setting_change`
  → V002 的 `ALTER TABLE` 报「no such table」（不是可容忍的 duplicate column）
  → `init_db` 返回 Err，且 `schema_version` **不含 2 也不含 3**。
- `v3_migration_failure_does_not_mark_version_as_applied`：删掉 `plot_item`
  → V003 的 `CREATE INDEX` 失败 → `init_db` 返回 Err，`schema_version`
  不含 3、保留 2，且 `novel` 计数仍为 1（失败没把库变成砖头）。

### 7.4 大数据迁移实测

命令：

```text
cargo test -p easy-writing-core --test migration_perf -- --ignored --nocapture --test-threads=1
exit 0，4 passed / 0 failed
```

数据集为**合成**数据（确定性正文，无随机数），实测于 macOS arm64 + 外置机械盘：

| 用例 | 数据集 | 库大小 | 造数据 | **迁移耗时** |
|---|---|---|---|---|
| `small` | 1 部作品 / 10 章 | 388 KB | 7.7 ms | **3.76 ms** |
| `thousand` | 1 部作品 / 10 卷 × 100 章 = **1000 章** | 12 324 KB | 111.5 ms | **3.97 ms** |
| `revisions` | 200 章 × 5 个历史版本 + 300 条设定变更 | 2 956 KB | 48.1 ms | **8.94 ms** |
| `lockcheck` | 1000 章 | 12 324 KB | 548.3 ms | **4.93 ms** |

结论与解释：

- 迁移耗时**与数据量基本无关**（388 KB → 3.76 ms，12 MB → 3.97 ms）。
  原因是 V002/V003 只做加列与建索引，索引建立在相对小的表上，
  正文数据本身不参与迁移。
- 1000 章库的重复初始化耗时 3.67 ms，即已完成迁移后再启动不会重跑。
- `lockcheck` 额外断言：迁移后 `PRAGMA journal_mode = wal`、
  `PRAGMA busy_timeout > 0`、连接池第二个连接**能立刻读到 1000 章**
  （证明未残留写锁）。
- **未设置 CI 性能阈值**：任务书要求阈值基于稳定 runner 实测，
  而本机是外置机械盘 + Apple Silicon，与 runner 差异是数量级的。
  脚本已支持 `EW_MIGRATION_GATE_MS`，但**故意没有写进 ci.yml**，
  需要先采集 runner 上的真实分布。
- 未发现死锁、数据损坏或不可接受的耗时。

### 数据安全影响评估

- 所有测试只使用 `std::env::temp_dir()` 下的隔离目录、临时数据库，
  以及 `127.0.0.1` 随机端口的进程内测试服务端。
- **未对用户真实数据库执行任何迁移、恢复、清空或覆盖操作。**
- 未删除任何已有备份；未自动清理用户指定目录。
  清理逻辑 `sweep_stale_candidates()` 严格限定在 `<64hex>.db.gz[.json]` 命名且超过 6 小时的自身临时文件。
- 清理了一次**由本次构建自己产生**的遗留物：`/Volumes/dmg.5UWQEe` 挂载卷与
  `rw.3892.Easy-writing_0.3.8_aarch64.dmg`（46 MB 构建中间态），
  均通过 `hdiutil info` 的 image-path 精确确认属于本仓库构建目录后才操作。
- 恢复前的安全快照保留到恢复被判定完全成功为止；回滚失败时保留且上报路径。
- 清单、错误信息、日志均不含真实 WebDAV 密码、API Key、钥匙串引用或作品正文；
  `PreservedLocalConfig` 不实现 `Debug` 从类型层面阻断误打印，
  并有专门用例 `config_restore_error_never_echoes_credentials_or_keychain_refs`。
- 未修改任何历史 migration 的业务语义。
- 未启动 GUI 应用，未触碰 `~/Library/Application Support/com.easywriting.desktop`。
