Easy-writing 审校报告-第三方
以下是本轮审校的重点。我将能够直接从源码推导出的行为，与需要实际运行才能验证的风险分开。
P0：切章保存仍有可能丢失正文
这是本次最需要优先处理的问题。
涉及文件：
- chapter_list.rs
- save_button.rs
- app_shell.rs
虽然 v0.3.5 已增加保存完成后才能切换的机制，但从当前源码来看，仍有两个边界没有被充分保护。

GitHub
+2



问题 A：保存失败时，章节切换保护会被绕过
目前 request_switch_chapter 的判断逻辑只检查：
if app_ctx.save_status.get() == "dirty" {
    // 打开未保存修改提示
} else {
    do_switch_chapter(app_ctx, target.id);
}


也就是说，它只对 dirty 状态进行拦截。
但如果自动保存失败，状态可能是 error。此时请求切章会直接进入切换流程，而不是再次提示用户保存失败、确认放弃或者重试。
如果当前正文还停留在编辑器内存中，切换到其他章节便可能覆盖未成功持久化的内容。相关判断可以在当前源码中直接看到。

GitHub



问题 B：保存成功不等于保存期间没有新增编辑
perform_save_async 在开始保存时记录 edit_seq，并在保存完成后检查用户是否又进行了输入。
这是合理的设计。但它的返回值目前表达的是 IPC 保存请求是否成功，而不一定表示保存期间的所有编辑均已写入数据库。

GitHub



与此同时，“保存并切换”的调用方使用这个返回值决定是否切章：
let ok = perform_save_async(app_ctx).await;

if ok {
    do_switch_chapter(app_ctx, tid);
}


这带来一个具体问题：假设本次保存请求写入了正文快照，但等待期间用户又输入了新文字，edit_seq 检查会让保存状态继续保持 dirty。然而，只要原来的数据库请求成功，调用方仍然可能切换章节。
而且，代码会在等待保存完成前关闭未保存修改弹窗。

GitHub
+1



这意味着最新输入可能尚未保存，编辑器就被切换到另一章节。
建议的修复方式
我建议把保存流程修改为明确的状态机：
保存结果	允许切章？
正文已保存，编辑版本号没有变化	允许
保存失败	不允许，保留提示窗口
保存期间发生新编辑	不允许，重新保存
当前保存仍在进行	暂缓切换
当前状态为错误且正文尚未持久化	必须重新确认或重试
不建议只返回一个 bool，而应该返回更明确的结果，例如 Saved、Failed、EditedDuringSave。
这是我认为当前版本应当优先完成的一项数据可靠性修复。 我没有在真实运行环境中复现数据丢失，但从现有控制流看，这条风险路径确实存在。
P1：AI Agent 请求失败后，可能无法自动重试
涉及文件：
extraction.rs
当前提炼流程会启动四类 Agent：世界观、角色、剧情和章节梗概。请求失败时，代码只处理成功返回的结果：
if let Ok(Ok(raw_json)) = task.await {
    // 解析并保存提炼结果
}


但在任务循环结束后，代码仍然会写入当前章节的 extracted_hash。

GitHub



问题在于：下一次对同一正文发起提炼时，系统先检查这个哈希。如果发现正文没变化，就会直接返回当前待审核候选项，而不会重新执行四个 Agent。

GitHub



这会产生以下后果：
1. 某个 Agent 因为 429 限流、网络中断或超时而失败。
2. 其他 Agent 可能成功，结果被保存。
3. 章节哈希仍然被标记为已提炼。
4. 对相同正文再次提炼时，失败的那个 Agent 可能一直没有机会补齐结果。
更合理的实现应为每种提炼任务单独记录状态，只把成功完成的 Agent 标记为完成；失败任务应支持按需重试。
P1：章节梗概的更新与去重逻辑可能互相冲突
这属于一个不容易从功能界面上看出来的数据一致性问题。
当前 build_existing_index 会构建角色、世界观和剧情条目的索引，但没有把 chapter_summary 纳入这一索引。

GitHub



在去重时，新建候选主要使用 kind + title 计算去重键；数据库查询则会把 pending、accepted 和 ignored 状态的同键记录全部视为已存在。

GitHub
+1



两者结合后，可能出现这种情况：
- 某章节已经提炼出一个梗概，并被用户采纳。
- 后续修改了该章节正文，再次触发提炼。
- 由于章节标题没变，新梗概仍然得到相同的创建型去重键。
- 已采纳的旧候选阻止新候选入库。
因此，同名章节的梗概可能无法在后续提炼中更新。
建议为章节梗概单独设计更新逻辑，利用 chapter_id 作为目标标识，并使去重规则能够识别“同一章节、不同梗概内容”的情况。
这项问题的实际影响取决于候选采纳逻辑和具体数据状态，但就当前提炼与去重函数的组合而言，值得优先修复并增加回归测试。
P1：设定更新和正文采纳没有严格串行
涉及文件：frontend/src/components/layout/app_shell.rs。
在冲突裁决的“更新设定并继续”处理里，当前代码会异步调用 apply_conflict_setting_update，但忽略该调用的结果；同时，正文插入操作在另一个控制路径上继续执行。

GitHub



因此，正文内容的采纳与设定库的更新没有形成严格的成功依赖。
如果设定更新失败，正文仍可能被插入，导致作者以为冲突已经处理，但设定库并未完成对应更新。
建议把两步放进同一个明确的异步流程：先确认设定更新结果，再插入正文；失败时显示错误并保留待处理内容，而不是静默继续。

四、AI Agent 的架构：有潜力，但还不算成熟的小说推理系统
这个项目的核心特色是从正文提炼世界观、角色、剧情和章节梗概，并将结果保存在候选区供用户审阅。它比完全让大模型自由写作更适合维护长期作品一致性。

GitHub
+1



但当前实现还有三个实际限制。
第一，每章提炼会重复发送正文。 当前共有四种提炼任务，使用相同的章节正文分别构造请求，并且最多允许两个模型请求同时执行。对于长章节，输入上下文和请求成本会明显增加。

GitHub



第二，模型拿到的既有设定索引有限。 当前提示词最多列出每类 200 个条目的 ID、标题和别名。即便本地已有完整设定索引，也不代表模型在一次请求中看到了所有人物详情和世界规则。

GitHub



第三，AI 的自动提炼与真正的长篇一致性检测不是一回事。 提炼成功，不代表系统能够可靠识别所有前后矛盾、长线伏笔和人物动机变化。尤其是百万字作品，需要检索、关系追踪、冲突检测和用户裁决共同配合。
我建议后续把 Agent 系统分成三个层次：
1. 事实提炼层： 识别人物、事件、设定和证据，失败可以重试。
2. 知识检索层： 根据当前章节检索相关人物、地点、规则和历史事件，不是把所有条目统一塞进提示词。
3. 冲突审校层： 明确显示冲突证据、可信度和相关章节，由作者做最终裁决。
这会比继续增加 Agent 数量更有价值。
五、安全与工程规范方面的检查结果
1. API Key 保护做得不错，但 API 地址安全仍可以加强
项目使用系统钥匙串保存模型 API Key，而不是把密钥直接写入 SQLite，这是值得肯定的设计。

GitHub
+1



但在当前 AiGateway 中，模型列表请求会向用户配置的 base_url 发起请求，并携带 Authorization 或对应协议的密钥头。当前这段逻辑没有看到按 HTTPS 限制远程请求的检查。

GitHub



对本地 Ollama 允许 HTTP 是合理的，但如果用户把远端供应商地址误配为 HTTP，API Key 可能经不加密连接发送。
建议实施以下策略：
- 远程地址默认要求 HTTPS。
- 仅对 localhost、127.0.0.1 等本机地址放行 HTTP。
- 对局域网 HTTP 端点要求用户显式确认。
- 在模型配置页面对不安全连接给出警告。
2. Tauri 的 CSP 建议补上
当前 src-tauri/tauri.conf.json 中的 csp 设置为 null。

GitHub



我没有据此认定当前应用已经存在可利用的 XSS 漏洞，但对一个需要处理用户导入的 EPUB、小说正文以及远端 AI 输出的桌面应用而言，禁用内容安全策略会减少一道防御层。
建议按实际资源和 IPC 需求配置最小权限 CSP，并对导入文档和 AI 返回内容坚持使用结构化渲染与明确的 HTML 清洗边界。
3. 发布安全仍有提升空间
当前 GitHub Actions 已在发布流程中运行测试，这是积极的。

GitHub
+1



但发布工作流还使用了带版本标签的第三方 Actions，并在整个发布任务范围内设置了 contents: write。对于生成可执行桌面应用的项目，建议进一步收紧供应链安全：
- 将关键第三方 Actions 固定到经过审核的提交 SHA。
- 把测试/构建任务与实际发布任务分开。
- 尽可能让构建任务使用只读权限，只在经过验证的发布步骤开放写权限。
- 逐渐加入安装包签名、公证与校验值发布。
此外，README 目前指导 macOS 用户通过 xattr -cr 清除整个应用包的扩展属性来绕过首次启动问题。

GitHub



比起让用户自行绕过系统保护，更好的方案是对正式发行包进行签名和公证。如果确实需要给出手动操作指导，应优先说明如何核对文件来源、哈希和签名，并尽可能只处理必要的隔离属性。
4. 版本号还存在元数据不一致
当前主分支的 package.json 和 Tauri 配置已经使用 0.3.5，但 src-tauri/Cargo.toml 与 frontend/Cargo.toml 的包版本仍显示 0.3.3。

GitHub
+3



这不一定会导致安装包的最终版本号错误，因为 Tauri 配置本身已经更新；但它会造成工程元数据不一致，影响诊断、构建信息和后续维护。
建议将这些版本号统一，并在 CI 中增加版本一致性检查。
