## 1. P0-1 备份完整性与恢复验证

### 1.1 新增能力：版本化备份清单

新增 `src-tauri/src/sync/manifest.rs`，产出旁挂的 `backup_xxx.db.gz.json`。

**为什么是旁挂文件而不是数据库新表**：清单要随备份一起上传到用户 WebDAV。
如果做成数据库内的表，它就只在「恢复成功之后」才存在 —— 而我们需要它恰好在
**恢复之前**来验证备份。旁挂文件让「校验」发生在破坏性操作之前。

清单字段（`BackupManifest`）：

| 字段 | 用途 |
|---|---|
| `manifest_version` | 清单格式版本，前向兼容判断 |
| `created_at` / `app_version` | 何时、哪个版本生成 |
| `schema_version` | 数据库 schema 版本 |
| `entity_counts` | 11 张业务表的行数（**刻意不含** `llm_profile` / `webdav_config`） |
| `assets[]` | `rel_path` / `size` / `sha256` |
| `compressed_size_bytes` | 压缩后体积 |

**向后兼容**：没有清单的历史备份走「结构完整性校验」分支，**不会被拒绝**。
这条是硬要求 —— 否则新增清单等于宣布所有旧备份作废。

**安全约束**：清单会离开用户机器进入 WebDAV，因此严禁包含凭据。
由两个测试守住：
- `manifest_never_contains_secrets` —— 造出含真实 key/url/pwd_ref 的库，
  断言序列化结果中不含这些字符串；
- `manifest_json_contains_no_secret_shaped_fields` —— 结构护栏，
  字段名里出现 `key`/`pwd`/`secret`/`token`/`url`/`username` 片段即失败。
  以后有人加字段时会立刻被提醒复核。

### 1.2 新增能力：恢复前预检（对应基线 C-02）

新增 `backup::preflight_backup()`，在**覆盖现有数据库之前**逐项检查：

| 检查 | 旧行为 | 新行为 |
|---|---|---|
| 是否 SQLite 文件 | `unwrap_or(0)` 伪装成 v0 合法旧库 | 只读打开失败 → 立即拒绝 |
| `PRAGMA integrity_check` | 无 | 必须返回 `ok` |
| `schema_version` | 读不到当 0 | 读不到 → 报错（不再放行） |
| 高版本备份 | 有检查 | 保留，并给出「请先升级」提示 |
| 实体计数 | 无 | 统计作品/卷/章/字数 |
| 空作品库 | 无 | 单独标记 `is_empty_library`，**不自动拒绝** |

**空库为什么单独标记而不是拒绝**：空库可能是作者真的清空过，也可能是备份损坏。
程序不替作者做这个判断 —— 但必须让他知道这件事发生了。

失败时的错误信息形如：
> 恢复中止：备份未通过完整性检查，原数据未被改动。数据库完整性检查未通过：…

恢复成功后，`RestoreReport.issues` 的**第一条**是恢复摘要，作者立刻能看到
「恢复到 schema v3、3 部作品 / 40 卷 / 512 章 / 87 万字」，而不是一个空报告。

### 1.3 新增能力：文件名校验（对应基线 C-01）

新增 `backup::validate_backup_filename()`，在 IPC 入口 `webdav_restore_backup`
最前面调用。拒绝：路径分隔符（`/` `\`）、相对段（`..`）、盘符（`:`）、
控制字符、NUL、空串。接受一切合法历史文件名（含中文）。

**为什么在入口而不是 `build_url`**：`build_url` 是通用 URL 拼接，
在那一层拦截会波及所有调用点；文件名是唯一来自前端的自由输入，
在入口挡住范围最小、意图最清晰。

### 1.4 轮转安全性重写（对应基线 C-03）

旧实现：上传完 → `move` 成功 → 立刻按数量删除第 21 个以后的备份。
**从不回读校验新备份**。

新实现在 `plan_rotation()` 中固化了三条不变量：

1. **新备份未验证通过时，一个都不删**（`new_backup_verified == false` → 返回空）。
2. **只处理 `backup_` 前缀的 `.db.gz`** —— 用户手动放进远端目录的其它文件
   不属于本应用的备份策略范围。旧实现只按 `.db.gz` 后缀过滤，会误删。
3. **删除失败不再静默**：汇总后向上返回 Err，作者能知道远端目录在无限增长。

同时修正了一处验证语义：旧代码把「服务端不支持 HEAD」和「校验通过」
用 `if let Ok(..)` 混为一谈 —— 不支持时整段大小校验被静默跳过，
却仍当作已校验。现在区分二者：无法确认远端状态 → 本次备份失败并清理，
而不是假装成功。

### 1.5 故障注入覆盖情况

| 场景 | 覆盖方式 | 状态 |
|---|---|---|
| 备份文件损坏（非 SQLite） | `preflight_rejects_non_sqlite_payload` | 已覆盖 |
| 上传截断 / 下载截断 | `preflight_rejects_truncated_database`（砍掉一半真实快照） | 已覆盖 |
| 压缩炸弹 | 恢复侧 256 MiB 上限 + EPUB 侧条目/总量/单条上限 | 已覆盖 |
| 路径穿越 | `backup_filename_rejects_path_traversal`（7 个恶意输入） | 已覆盖 |
| 轮转误删 | `rotation_only_considers_recognised_backup_names` | 已覆盖 |
| 未验证即轮转 | `rotation_never_drops_below_verified_backup_count` | 已覆盖 |
| 旧备份兼容 | `backup_filename_accepts_legacy_and_current_formats` + 清单 `read_sidecar` 返回 `Ok(None)` 分支 | 已覆盖 |

### 1.6 覆盖缺口（明确记录，未验证即未验证）

- **未对真实 WebDAV 服务端（坚果云 / Nextcloud 等）执行过任何集成测试。**
  因此「上传中断」「远端 MOVE 失败」「服务端是否支持 HEAD」这三类行为
  在真实服务端上的表现**未经验证**。`webdav.rs` 的 367 行代码目前只有
  解析函数级别的间接覆盖。
- 磁盘空间不足场景未构造。本机外置盘剩余 797 GiB，构造满盘需要额外环境。
- 上述缺口不影响「恢复前预检」这一层保护的正确性 —— 预检纯粹作用于
  已经落到本地的字节，与服务端行为无关。

## 2. P0-2 SQLite 迁移与异常恢复

### 2.1 事务缺口修复（对应基线 C-05）

`db/trash.rs` 的 `purge_trash_item` 与 `empty_trash` 原来是顺序执行的裸 DELETE
（分别为 2 条与 5 条）。磁盘满 / 库被锁时，前几条已提交、后几条未执行，
留下「章节没了但卷还在」「设定清空了但人物还在」且**无法回滚**的残局。

改为 `conn.transaction()` 包裹整组语句，签名从 `&Connection` 收紧为
`&mut Connection`（rusqlite 的 `transaction()` 需要独占引用，这是编译期保证）。

调用方同步更新：`commands/mod.rs` 的两个命令改为 `let mut conn`。

**兼容性**：成功路径行为完全一致；失败路径从「半删除」变成「什么都没删」。

新增测试 3 个（`novel_trash.rs`）：原子性、跨作品隔离、删卷不删作品。

### 2.2 审计结论：迁移体系无需重写

基线审计已确认迁移阶梯（`schema_version` 表 + 按序执行 + `INSERT OR IGNORE`
防并发首启 + 只白名单 `duplicate column` 错误）**质量良好**，
且已有 `migration_ladder.rs` 3 个用例覆盖幂等性与老库补列。

因此本次**未改动迁移体系**，符合任务书「不重复实现已经存在的能力」。

### 2.3 仍未覆盖

- **历史 schema 连续升级路径（v1→v2→v3）未测试**。现有测试只构造了
  「缺列老库」一种形态，没有从真实 v1 库逐级升级到 v3 的用例。
- **大数据量迁移**（千章级作品升级耗时与锁表表现）未测量。
- 数据库诊断界面（P0-2 任务 D）**未实现**。

## 3. P0-3 发布、版本与安装验证

### 3.1 版本一致性门禁（新增）

新增 `scripts/check-version.mjs`，覆盖仓库中全部 5 处版本字段
（`package.json`、3 个 `Cargo.toml`、`tauri.conf.json`）与 `CHANGELOG.md`。

规则有意分层：

- **必须一致**：5 处构建相关字段 —— 它们都进入产物元数据。
- **仅告警**（`--strict` 下转为失败）：CHANGELOG 条目缺失。
  缺失是流程问题而非产物错误，硬阻断会让「先发版再补 changelog」卡死。

**修复了一个自查中发现的真实缺陷**：初版只解析 `--tag=v0.3.8`，
而 CI 里写的是 `--tag "$GITHUB_REF_NAME"`（空格分隔），
导致错误 tag 竟然通过了检查。现已同时支持两种写法并实测验证。

接入两个工作流：
- `ci.yml` 新增 `version` job，**放在最前面** —— 版本错了，
  后面所有构建与测试的结论都无意义。
- `release.yml` 在 `pnpm test` 之前插入 tag 校验，tag 与配置版本不一致即终止发布。

### 3.2 安装冒烟测试：未执行（明确标记）

任务书 P0-3 要求「实际安装与启动测试有执行证据」。**本次未执行。**

原因：本会话运行在作者的开发机上，没有 macOS 签名证书、没有 Windows 代码签名证书，
也没有 GitHub Actions runner 的 macOS/Windows 环境。任何声称「安装测试已通过」
的说法都会是虚假的。

CI 中已有的门禁（且确实会运行）：`pnpm test` 全量测试 + 版本校验。
这是本次能提供的**真实**证据边界。

### 3.3 签名与公证：未配置

`tauri.conf.json` 的 `bundle` 段只有图标与 `active: true`，
**没有 `macOS.signingIdentity` / `notarization` / `windows.certificateThumbprint`**。
当前发布的安装包是未签名、未公证的。

这在基线报告中记为 `Risk R-06`，本次未处理 —— 它需要证书与付费的
Apple Developer 账号，不属于代码可解的范围。
