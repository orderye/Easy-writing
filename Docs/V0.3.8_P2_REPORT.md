# V0.3.8 · P2 阶段报告（创作体验与 AI 结果可信度）

> **本阶段未实现任何新功能。**
>
> 这是**刻意的范围决策**，不是遗漏。任务书 6 明确写着：
> 「P2 的目标是建立在 P0、P1 已有保护措施之上，不应在数据安全问题尚未解决时引入大规模新功能。」
>
> 本文件记录的是**审计结论**与**可执行的分期计划**，
> 供后续版本接手 —— 而不是把计划写成已完成。

---

## 1. 为什么本阶段不做功能

### 1.1 任务书的前置条件未满足

任务书对 P2 的定位是「建立在 P0、P1 已有保护措施之上」。实际情况：

| 前置条件 | 状态 |
|---|---|
| P0 关键数据保护测试全部通过 | ✅ 本次完成（备份预检 / 轮转 / 事务 / 发布门禁） |
| 安装冒烟测试有执行证据 | ❌ **未执行**（无证书、无 runner 环境） |
| 性能基线可复现 | ⚠️ 后端已建立，前端未测 |
| CI 性能门槛确定 | ❌ 未定（需 CI runner 上采集分布） |
| 依赖漏洞扫描接入 CI | ❌ 未做 |

其中**安装冒烟测试**是发布条件之一（P0-3 验收标准明确要求
「至少有真实运行证据支持安装冒烟测试结论」）。它未执行意味着
**P0 的发布门禁本身没有闭环**。

在这个状态下引入设定证据链、连续性检查、AI 修改审阅等新功能，
等于在未验证的地基上盖楼 —— 与任务书「不因赶版本而跳过 P0」的指令相悖。

### 1.2 现有模型已经能承载一部分需求

审计 `db/settings.rs`（685 行）与 `db/extraction.rs` 后发现：
`extraction_candidate` 表**已有** `chapter_id`、`evidence`（原文证据）、
`agent_id`、`dedup_key`、`created_at` 等字段，
`setting_change` 表**已有** `target_type`、`target_id`、`before_content`、
`after_content`、`reason`、`target_title`、`is_reverted`。

也就是说 P2-1「设定证据链」所需的**大部分字段已经存在**，
真正缺的是「来源正文变化后如何标记候选过期」这一层逻辑，
以及来源片段的可靠性校验。

这属于**在已有模型上补一层逻辑**，不需要新表 ——
工作量比任务书预估的小，但**前提是先把 P1 的测试跑稳**。

## 2. P2-1 设定证据链：审计结论与计划

### 2.1 已有能力（无需重建）

| 需求 | 现状 |
|---|---|
| 候选关联来源章节 | ✅ `extraction_candidate.chapter_id` |
| 保存原文证据 | ✅ `extraction_candidate.evidence` |
| 记录生成方式 | ✅ `agent_id` |
| 设定变更审计 | ✅ `setting_change` 全套（含撤销 `is_reverted`） |

### 2.2 缺失能力与建议实现顺序

| 步骤 | 内容 | 风险 |
|---|---|---|
| 1 | 为 `extraction_candidate` 增加来源指纹（章节内容哈希） | 低：纯新增列 |
| 2 | 保存时记录 `source_fingerprint`；读取时与章节当前指纹比对 | 低 |
| 3 | 不一致时给候选加 `stale` 视觉标记，**不自动覆盖作者已确认的设定** | 中：涉及 UI |
| 4 | 提供「查看原文」跳转 | 低 |

**关键设计约束**（P2-1 任务 B 已指出，必须遵守）：
若使用字符偏移定位，正文一改就会失效。
本仓库 `asset.rs` 的注释里已经确立了正确做法 ——
**按内容哈希匹配而非按路径或行号**，并保留章节级回退。
证据链应遵循同一原则。

### 2.3 明确不做

- **不伪造行号/字符偏移**。`evidence` 是文本片段而非位置引用，
  展示时应作为「疑似来源」而非「精确定位」。
- **不自动覆盖已确认设定**。作者确认过的 `setting_change` 不得被 AI 静默修改。

## 3. P2-2 全书连续性检查：审计结论

### 3.1 已有基础

`src-tauri/src/ai/consistency.rs`（6250 字节）已存在，
`commands/mod.rs` 注册了 `ai_check_conflict`，
`shared_types::ConsistencyOutcome` 已有四态枚举：

```
Applied / Reverted / Conflict / NotChecked   （见 shared-types/lib.rs:301）
```

且 `NotChecked` 已实现 `is_not_checked()`。这是一个**已有的结果模型**，
不是需要从零设计的东西。

### 3.2 任务书要求的七类检查 vs 现状

| 检查项 | 现状 |
|---|---|
| 人物年龄与时间线冲突 | ❌ 无 |
| 身份、称谓、关系变化 | ⚠️ 有 `character_relation`，但无冲突检测 |
| 能力/装备/规则冲突 | ❌ 无 |
| 事件与后续描述不一致 | ❌ 无 |
| 物品持有者/位置冲突 | ❌ 无（且无「物品」实体表） |
| 角色状态冲突 | ❌ 无 |
| 章节顺序与事件时间 | ❌ 无 |

**结论：七类检查中六类完全不存在。** 这不是「补齐边界」，
而是新建一套子系统，涉及：

- 新的数据模型（时间线、事件、物品持有关系）
- 新的提取流程
- 新的证据组织方式
- 新的审阅 UI

工作量远超本次可靠性专项的合理范围。

### 3.3 误报控制的既有线索

任务书 P2-2 任务 B 要求区分「确凿冲突」与「模型推测」。
`ConsistencyOutcome` 的四态设计已经是这个方向的第一步，
后续应在结果中显式携带**证据片段**与**可信度**，而不是只给结论。

### 3.4 建议

**整个 P2-2 推迟到下一个独立版本**，理由如上。
若要做，必须先有：
1. 设定证据链（P2-1）落地 —— 否则「关联设定」无从谈起；
2. 章节级时间戳数据 —— 当前 `chapter` 表**没有故事内时间字段**，
   时间线冲突检测缺少最基础的数据。

## 4. P2-3 AI 修改审阅与撤销：审计结论

### 4.1 已有能力（比任务书预期的好）

| 需求 | 现状 |
|---|---|
| 变更预览 | ✅ `setting_change.before_content` / `after_content` |
| 差异对比 | ✅ `DiffFixes` 机制（`tests/diff_fixes.rs` 5 个用例） |
| 采纳/拒绝 | ✅ `apply_conflict_setting_update` |
| 撤销 | ✅ `setting_change.is_reverted` + `revert_setting_change` |

### 4.2 缺失能力

| 需求 | 现状 |
|---|---|
| AI 直接改正文并先审阅后采纳 | ❌ 无。`ai_polish` 存在，但需确认是否走审阅流程 |
| 并发编辑保护（AI 建议不得覆盖用户新输入） | ❌ 无 |
| 正文级的变更历史与撤销 | ⚠️ 有 `chapter_revision`，但与 AI 建议未打通 |

### 4.3 关于并发保护的判断

这一点**值得单独强调**，因为它与前端已有的设计直接相关：
`frontend/src/save_state.rs` 已经为**用户手动切章**实现了
`SwitchSafetyOutcome` + `edit_seq` 比对机制，专门防止「异步读取期间键入的新内容
被新章节冲刷覆盖」。

AI 修改正文面临**同一类竞态**，但保护机制**不能直接复用**：
- 切章是「读另一个章节」，冲突对象是 `current_edit_seq`；
- AI 改写是「写回同一章节」，需要在采纳时校验
  「AI 生成期间正文是否已变」。

因此 P2-3 的并发保护需要**新的一套校验**，不能假设现有状态机已经覆盖。

## 5. P2-4 作品诊断与恢复中心：可立即实现的部分

这是 P2 中**唯一可以在后续版本快速交付**的模块，因为它主要是**只读聚合**。

### 5.1 已有的诊断数据源（全部现成）

| 诊断项 | 数据来源 | 状态 |
|---|---|---|
| 素材引用失效 | `asset::scan_storage()` → `ImageScanReport.missing_records` | ✅ 已有 |
| 孤儿文件 | `asset::scan_storage()` → `orphan_files` | ✅ 已有 |
| 钥匙串凭据失效 | `restore.rs` 的 `DanglingKeyInfo` 逻辑 | ✅ 已有（仅恢复时跑） |
| 数据库完整性 | 新增的 `backup::preflight_backup()` | ✅ 本次新增 |
| 迁移状态 | `SELECT MAX(version) FROM schema_version` | ✅ 已有 |
| 数据库/素材路径 | `commands::get_app_data_dir` | ✅ 已有 |

### 5.2 缺失的诊断项

| 诊断项 | 说明 |
|---|---|
| 最近备份时间与结果 | 需要记录一次成功备份的时间戳（当前不持久化） |
| 未完成/失败的 AI 任务 | **依赖 P1-2 的任务持久化，本次明确未做** |
| 可用磁盘空间 | 未实现 |
| 异常退出恢复点 | 当前架构不支持（无崩溃恢复机制） |

### 5.3 关键设计要求（与任务书一致）

- **诊断与修复分离**；`asset::prune_orphan_images()` 已经是「只删确认无引用」的实现，
  符合这个原则，可直接复用。
- **默认只读**，不自动删除任何记录或文件。
- 单项诊断失败不得阻塞其他项 —— 需要逐项 `catch` 而非整体 `?`。
- 不把凭据与正文写入诊断报告。

### 5.4 建议

P2-4 可以在 V0.4.0 作为第一个 P2 交付项：
它主要是对**本次新增能力**（预检）与**已有能力**（存储对账、钥匙串体检）的聚合展示，
不涉及新数据模型，风险低、收益直接。

## 6. P2-5 命令面板与写作体验：推迟

理由与 P2-2 相同：无新数据模型、无新后端能力，纯前端功能。
在可靠性专项中引入前端新功能，会分散对「数据是否安全」的验证注意力。

**唯一值得记录的观察**：`db/chapter.rs::find_chapters_mentioning` 使用
`LIKE '%term%'`，前置通配符导致无法走索引。
如果将来做全局搜索，这是**首要优化点**，
且 `perf_benchmark.rs` 的 `perf_fulltext_search_baseline` 已经为它建立了基线，
优化前后可直接对比。
