# V0.3.8 · 迁移、回滚与恢复策略

> 本文件说明 V0.3.8 **实际做了什么**，以及出问题时**怎么退回去**。

---

## 1. 结论先行

**V0.3.8 没有新增任何数据库迁移，也没有改变任何数据表结构。**

这不是省事，而是刻意的：可靠性专项的第一条原则是「不冒数据风险换功能」。
基线审计确认现有迁移阶梯（`schema_version` 表 + 按序执行 + `INSERT OR IGNORE`
防并发首启）质量良好且有测试覆盖，因此**未改动迁移体系**。

唯一的例外是 `purge_trash_item` / `empty_trash` 的**事务边界调整**，
但它不改变 schema，只改变「多条 DELETE 是否同生共死」。

---

## 2. 数据库侧变更

### 2.1 无 schema 变更

| 项目 | 状态 |
|---|---|
| 新增表 | 无 |
| 新增列 | 无 |
| 新增索引 | 无 |
| 删除字段 | 无 |
| 字段语义变更 | 无 |
| 迁移文件 | 无新增（仍为 V001 / V002 / V003） |
| `BASELINE_VERSION` | 仍为 `3`，未变 |

因此：

- 0.3.7 → 0.3.8 的升级**不需要任何数据转换**。
- 0.3.8 生成的备份可被 0.3.7 恢复（schema 版本未变，仍 ≤ `BASELINE_VERSION`）。
- 0.3.7 生成的备份可被 0.3.8 恢复（无清单走兼容分支）。

### 2.2 行为变更：回收站批量删除

**变更前**：`purge_trash_item`（2 条 DELETE）与 `empty_trash`（5 条 DELETE）
顺序执行裸语句。

**变更后**：整组包进事务。

**失败场景的行为差异**：

| 场景 | 变更前 | 变更后 |
|---|---|---|
| 全部成功 | 5 张表都清空 | 5 张表都清空（**一致**） |
| 第 3 条失败 | 前 2 张表已提交，后 3 张未删 —— **残局无法回滚** | 事务回滚，**一张都没删** |

**兼容性**：成功路径完全一致。API 签名从 `&Connection` 变为 `&mut Connection`
（`rusqlite::transaction()` 要求独占引用，这是编译期强制），
已同步更新全部调用方：`commands/mod.rs` 两个命令、`tests/novel_trash.rs`。

### 2.3 回滚方案

若 0.3.8 出现问题需要回退：

1. **数据库无需回滚** —— 没有任何 schema 变更。
2. 回退安装包到 0.3.7 即可，数据库文件可直接被 0.3.7 打开。
3. 若要撤销代码改动：`git revert` 对应提交即可。

## 3. 备份格式变更

### 3.1 变更内容

| 项目 | 变更前 | 变更后 |
|---|---|---|
| 备份文件本身 | `backup_<ts>.db.gz` | **不变** |
| 上传方式 | `.tmp` + `MOVE` | **不变** |
| 清单 sidecar | 无 | **新增** `backup_<ts>.db.gz.json` |
| 轮转规则 | 按数量删第 21 个之后 | **收紧**：仅在新备份验证通过后执行，且只处理 `backup_` 前缀 |
| 图片写入 | `fs::write`（可能截断） | **原子写**（临时文件 + rename） |

### 3.2 向后兼容性（重要）

**没有清单的历史备份依然可以恢复。**

`manifest::read_sidecar()` 在 sidecar 不存在时返回 `Ok(None)`，
此时恢复流程走纯结构完整性校验分支，并在 `RestoreReport` 中注明
「该备份没有清单文件（历史备份），已按结构完整性校验通过」。

不会因为「新增了清单」而拒绝任何旧备份。这一点是硬要求。

### 3.3 备份兼容性矩阵

| 备份来源 | 0.3.8 能否恢复 | 说明 |
|---|---|---|
| 0.3.7（无清单） | ✅ 可以 | 走结构校验兼容分支 |
| 0.3.8（有清单） | ✅ 可以 | 校验清单与实际实体数 |
| 更高版本的备份 | ❌ 拒绝 | schema 版本 > `BASELINE_VERSION`，提示先升级软件 |
| 损坏 / 非 SQLite | ❌ 拒绝 | `PRAGMA integrity_check` 不通过 |
| 高版本备份恢复到旧版客户端 | ❌ 拒绝 | 同上，版本检查保留 |

### 3.4 恢复失败时的保护

**本次没有改变恢复的保护点机制**，它本来就存在：

`restore.rs:28-49` 在覆盖前先生成本地 `pre_restore_<ts>.db` 快照。

**本次新增的是「更早的一道门」**：现在覆盖发生前必须先通过完整性预检。
也就是说，损坏备份在**触碰目标数据库之前**就被拒绝，
而不是先覆盖再发现有问题。

## 4. 恢复流程（0.3.8 实际顺序）

```
1. 文件名白名单校验（拒绝路径穿越）
2. 本地 pre_restore 快照（保护点，原有）
3. 暂存本地 WebDAV 配置与外观设置（避免被远端全库覆盖，原有）
4. 从 WebDAV 下载 .db.gz
5. 分块解压，超过 256 MiB 立即中止            ← 新增
6. 写入临时文件
7. ★ 预检：                                        ← 新增
     ├─ 只读打开（失败 = 不是 SQLite，拒绝）
     ├─ PRAGMA integrity_check（失败 = 拒绝）
     ├─ schema_version 读取（失败 = 拒绝，不再 unwrap_or(0)）
     ├─ 高版本检查（超过 BASELINE = 拒绝并提示升级）
     └─ 实体计数 + 空作品库标记
8. 与 sidecar 清单对照（可选，缺失不拒绝）
9. SQLite Backup API 覆盖目标库
10. 恢复暂存的本地配置
11. 图片补回：逐张 SHA-256 校验 + 原子写         ← 原子写为新增
12. 钥匙串 key_ref 有效性体检
13. 返回 RestoreReport（含恢复摘要 + 全部问题）
```

**第 7 步是本次最重要的变化**：任何一项不过都在覆盖前中止，
错误信息形如「恢复中止：备份未通过完整性检查，原数据未被改动」。

## 5. 用户需要执行的操作

**无。**

- 没有数据迁移需要手工触发。
- 没有新的必填配置。
- 没有格式不兼容。

唯一的用户可见变化是**行为更严格**：过去某些会被接受的损坏备份现在会被拒绝，
并给出明确原因。这是预期行为。

## 6. 故障排查路径

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 「备份不是有效的 SQLite 数据库」 | 下载的是 HTML 错误页，或传输中被替换 | 检查 WebDAV 凭据；重试 |
| 「数据库完整性检查未通过」 | 上传/下载中断，文件损坏 | 用别的备份恢复 |
| 「该备份由更高版本生成」 | 客户端版本低于备份版本 | 先升级 Easy-writing |
| 「备份没有清单文件」 | 历史备份 | **正常**，非错误 |
| 「恢复后素材缺失」 | `RestoreReport.issues` 中列出 | 按 issue 中的文件名检查 WebDAV images 目录 |
| 「远端目录会持续增长」 | 轮转删除失败 | 错误信息中列出了失败的文件名 |
