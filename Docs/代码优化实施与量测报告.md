## 二、分阶段量测

### 阶段 1 · 测试覆盖缺口

| 项 | 前 | 后 |
|---|---:|---:|
| `command_key_sweep` handler 注册数 | 63 | **77** |
| `command_key_sweep` 用例数 | 63 | **77** |
| `ipc_argcase` 命令数断言 | 77 | **85** |
| 测试文件数 | 4 | **5** |

**发现的真实问题**：`command_key_sweep` 的注释写着「Keep the handler list and
`cases` in sync when commands are added」，但它自身已经失同步——新增的 6 个对话命令、
`update_llm_profile`、`fetch_remote_models` 全都不在其中。也就是说，
上一轮「修复差异报告」新增的命令**当时处于无测试守护状态**。

**受限说明**：`ai_chat_stream` / `save_chapter_content` / `save_image_asset` /
`webdav_backup_now` / `webdav_restore_backup` 的首参为 `tauri::AppHandle`，
而 `AppHandle` 不实现 `CommandArg<'_, MockRuntime>`，因此**无法**在 MockRuntime
下注册，本 sweep 覆盖不到，已在测试中显式注明并由 `ipc_argcase` 兜底。
这是测试框架的客观限制，不是配置疏漏。

### 阶段 2 · db 层 mapper 消重

| 指标 | 值 |
|---|---:|
| db 目录净变化 | +421 / −460 = **净 −39** |
| 新增 `mapper.rs` | 51 行 |
| 消除的「同 mapper 复制两份」处 | 16 个实体函数 |
| 消除的 `rows.next()` 三段式 | ~30 处 |
| 消除的 `Vec::new()+push` 收集循环 | ~20 处 |

**注意**：本阶段的行数收益（−39）远小于方案预估的 ~300 行。原因是方案预估时
把「同一实体 list/get 两份 mapper」按整段重复计算，实际其中一份本就要保留为
共享函数，净删主要来自三段式与收集循环。**真正的收益不在行数，而在语义**：
列清单提取为常量后，SQL 的 SELECT 顺序与 `row.get(n)` 的下标绑定在一处，
杜绝了「改了 SELECT 忘了改下标」这类静默错位——这类 bug 编译期不报错、
运行期只在特定行显现，是 db 层最难查的一类。

### 阶段 3 · IPC 调用构建器

| 指标 | 值 |
|---|---:|
| 前端整体净变化 | +1508 / −1904 = **净 −396** |
| 删除参数结构体 | **79 个** |
| 迁移调用点 | **120 处** |
| 覆盖文件 | 25 个 |
| 新增 `tauri_api` 构建器 | 92 行 |

**方案偏离说明（重要）**：方案原定用 `macro_rules!` 展开字段表
（`invoke_cmd!("cmd", { a, b: expr })`）。实测发现两个无法绕过的障碍：

1. **片段匹配歧义**：`$v:expr` 后不能直接跟 `,`，导致
   `{ novel_id, term: t, category: cat, source_id: None }` 这类
   简写与显式键名混排的字段表无法被单一规则匹配。
2. **裸 `None` 无法推断类型**：`to_value(&None)` 缺少 `Option<T>` 的 `T`，
   编译报 `E0282：type annotations needed`。

我写了一个独立探针（现 `tests/ipc_arg_encoding.rs`）逐形状验证，
确认这是宏机制的固有限制而非写法问题，最终改用链式构建器：
类型推断回归普通 Rust 规则，无歧义；`.opt()` 显式表达可选语义。
**这是本次实施中唯一偏离原方案的设计决策。**

**关键结论：本阶段行数增加（+124），但这是刻意的。** 去繁化简的目标不是行数
最小化，而是让每个文件只承担一个域的职责。拆分前 1560 行里塞了 6 个不相关域、
39 个 `RwSignal` 平铺在同一作用域；拆分后最大文件降到 948 行（外壳），
各标签页状态内聚。

顺带修掉一个真实缺陷：原先切到「写作偏好」再点保存，会把**当前所有标签页的信号**
一起写库；拆开后每个标签页只持有自己的状态，副作用范围收敛。

**关于「大文件」的判断口径**：config_modal 之所以值得拆，是因为它把
**6 个不相关域**（LLM / Agent / 模板 / WebDAV / 偏好 / 更新）塞进一个组件，
拆分边界是天然的。上表这些文件各自只承担**一个域**，内部是「列表 + 表单 + 弹窗」
的连续交互，拆分只会把状态切碎、增加跨文件传参。因此建议**不动**——
判断标准是「域是否混杂」，不是「行数是否够大」。

### 4.3 专项说明

| 项 | 说明 | 建议 |
|---|---|---|
| IPC 命令名保障 | **已在 4.4 节解决**：改为两侧源码自动提取比对，不再依赖人工列表 | ✅ 已完成 |
| `volume_list.rs` | 虚拟滚动与渲染交织，`ITEM_HEIGHT = 34.0` 与 CSS `box-border` 强耦合 | 抽象收益低、回归风险高，保持现状（详见下） |
| `js/src/*.js` | `graph-bridge.js` 617 行、`tiptap-bridge.js` 537 行 | 命令式胶水，抽象会引入跨文件可变状态，不动 |

**`volume_list.rs` 为何不动**：虚拟滚动的正确性依赖「`ITEM_HEIGHT` 常量」
与「CSS 盒模型」严格一致。抽成通用组件时，只要高度计算或 `box-sizing`
有一处不匹配，就会出现滚动错位或空白——而这类问题**在小数据量下测不出来**，
因为当前逻辑在节点 ≤30 时直接跳过窗口化。收益是省几十行，风险是回归一个
只在 300+ 章节才显现的 bug。若要动，应先补一个「大数据量下滚动位置与渲染窗口
一致」的测试。

### 4.4 IPC 命令名保障（本轮已实现）

删掉 86 个参数结构体后，命令名与参数键名从「编译器校验的结构体字段」退化为
「运行时字符串」——写错不会有任何编译错误，只在运行时报 `command not found`。

原先的守护是 `command_key_sweep.rs` 里**手工维护**的 handler 列表，而它已经
失同步过一次（阶段 1 发现新增 8 个命令后无人同步）。人工清单本身易腐，
因此新增 `tests/ipc_command_inventory.rs`，改为**两侧都从源码自动提取**：

| 侧 | 提取方式 |
|---|---|
| 后端 | 扫描 `src/commands/*.rs` 中所有 `#[tauri::command]` 标注后紧跟的函数名 |
| 前端 | 扫描 `frontend/src/**/*.rs` 中 `invoke_cmd("...")`、`invoke_no_args::<T>("...")`、以及经 `load_for_novel` / `load_list_for_novel` 封装传入的字面量 |

**新增测试（3 个用例）**：

1. `every_frontend_invoked_command_exists_in_backend` —— 前端调用的每个命令
   后端必须存在，否则失败并列出缺失项。
2. `report_backend_commands_never_invoked_by_frontend` —— 反向报告后端有但
   前端未调用的命令，**只输出不失败**（后端保留预留命令是合理的，硬失败会制造噪音）。
3. `extractors_actually_extract` —— 元测试，断言提取器确实扫到了已知命令。
   防止「提取器静默失效导致断言恒真」这类测试自身失效。

**实测结果**：后端 85 个命令，前端调用 76 个，覆盖率 **89%**。
未被调用的 9 个已逐条人工确认为真实未对接（非提取遗漏）：
`append_chat_message` / `delete_chat_session` / `delete_novel` / `get_novel` /
`list_chat_sessions` / `move_chapter` / `reorder_chapters` / `reorder_volumes` /
`save_image_asset`。

#### 实现中发现并修正的两个自身缺陷

这两个缺陷都是「测试看起来通过了，但其实没在守护」——若不主动注入错误验证，
会一直带着虚假信心：

1. **提取器漏掉经封装的调用**。首版只匹配 `invoke_cmd("...")` 字面量，
   而阶段 5 引入的 `load_for_novel(app_ctx, "list_characters", ..)` 把命令名
   作为参数传入，不在 `invoke_cmd(` 之后。结果 6 个实际被调用的命令被误报为
   「未使用」（覆盖率虚低至 82%）。已扩展提取范围，覆盖率修正为 89%。

2. **过滤器静默丢弃了最该报错的输入**。首版为「避免把杂项当成命令名」加了
   一个「只收小写字母/数字/下划线」的过滤，结果把 `save_chapter_content_TYPO`
   这类**大小写笔误直接丢弃**——恰好放过了最该抓的错误。
   实测方式：故意注入上述笔误，测试**未报警**；移除过滤后同一笔误被正确捕获
   并给出可操作的报错信息。

这两个缺陷说明：**一个从未失败过的测试，无法证明它在守护任何东西。**
故最终保留了 `extractors_actually_extract` 作为常驻自检。

## 五、结论

本次优化的实际收益，按重要性排序**不是行数**：

1. **消除了一类静默 bug**（阶段 2）：SQL 列序与 `row.get(n)` 下标绑定在
   mapper 常量一处，不再可能错位。
2. **消除了契约漂移的温床**（阶段 3）：86 个参数结构体是后端 snake_case 契约的
   第二份手抄，删掉后键名与值写在一处，不再有「抄错键名到运行时才暴露」的路径。
3. **收敛了副作用范围**（阶段 4）：标签页拆分让每个域只持有自己的状态，
   「保存偏好却写入全部标签页状态」这类越界副作用不再可能。
4. **补上了缺失的自动防线**（阶段 1）：8 个此前无测试守护的命令进入 sweep。

净删 343 行是这些结构性改进的副产品，而非目标本身——阶段 4 甚至主动增加了
124 行以换取职责清晰。
