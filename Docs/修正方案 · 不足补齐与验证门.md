### 执行中被推翻的两个判断（保留记录，避免后来者重走）

1. **`AppHandle` 能否注册到 MockRuntime** —— 方案原判断「仓库注释过期」是**错的**。
   实测编译报 E0277：命令声明的是 `tauri::AppHandle`（即 `AppHandle<Wry>`），而
   `impl<'de, R: Runtime> CommandArg<'de, R> for AppHandle<R>` 要求 `R` 与注册时的 Runtime 一致，
   因此不满足 `CommandArg<MockRuntime>`。`command_key_sweep.rs` 与 `ipc_argcase.rs` 里那两处注释是准确的。
2. **不要新增 `pnpm-workspace.yaml`** —— pnpm 12 会自动生成它并让 install 报 `ERR_PNPM_IGNORED_BUILDS`，
   看着很像「补个配置就好」，但本仓库此前已因此失败并回滚（commit `33dffdb`）。用 `packageManager` 钉版本即可。

### P0-3 保存状态机竞态（新发现，优先级高）

**问题**：保存期间用户继续输入，会把新内容误标记为"已保存"，随后切章会静默丢弃这段输入。

- `frontend/src/components/structure_panel/save_button.rs:8` 先把状态置为 `"saving"`；
- 第 21 行起 `spawn_local`，IPC 返回后第 32 行无条件置 `"saved"`；
- 与此同时 `frontend/src/components/editor/editor_wrapper.rs:24` 的 `onUpdate` 会置 `"dirty"`；
- 若"置 dirty"发生在"置 saved"之前（保存耗时 > 用户下一次击键），最终状态为 `"saved"`，但磁盘上的内容**早于**编辑器内容；

1. `frontend/src/state/mod.rs` 的 `AppContext` 增加：

```rust

    pub edit_seq: RwSignal<u64>,
```

2. `frontend/src/components/editor/editor_wrapper.rs` 的 `onUpdate` 改为：

```rust
Closure::wrap(Box::new(move || {
    edit_seq.update(|n| *n += 1);
    save_status.set("dirty".to_string());

}) as Box<dyn FnMut()>)

3. `frontend/src/components/structure_panel/save_button.rs` 的 `perform_save` 改为记录并比对序号：

```rust
pub fn perform_save(app_ctx: AppContext) {
    if let Some(mut chapter) = app_ctx.current_chapter.get() {
        let seq_at_save = app_ctx.edit_seq.get_untracked();
        app_ctx.save_status.set("saving".to_string());
        let content_json = tiptap::get_content_json();
        let content_plain = tiptap::get_content_plain();
        let word_count = tiptap::get_word_count() as i32;
        // ... 原有赋值与 chapter_id 提取不变 ...

        leptos::task::spawn_local(async move {
            let res = invoke_cmd("save_chapter_content")
                /* 参数不变 */
                .send_unit()
                .await;

            let edited_since = app_ctx.edit_seq.get_untracked() != seq_at_save;
            match res {
                Ok(_) if edited_since => app_ctx.save_status.set("dirty".to_string()),
                Ok(_) => app_ctx.save_status.set("saved".to_string()),
                Err(err) => {
                    web_sys::console::error_1(&format!("Failed to save chapter: {}", err).into());
                    app_ctx.save_status.set("error".to_string());
                }
            }
        });
    }
}
```

**这个状态机可以脱耦成纯函数做单测**（不依赖 DOM），建议同时抽出：

```rust
/// 保存完成后的目标状态。纯函数，便于单测三种组合。
pub fn resolve_save_status(succeeded: bool, edited_since: bool) -> &'static str {
    match (succeeded, edited_since) {
        (false, _)      => "error",
        (true, true)    => "dirty",   // 保存期间又有新编辑，不能标记为已保存
        (true, false)   => "saved",
    }
}
```

### P0-4 自动保存失败后不再重试

**问题**：`frontend/src/components/layout/app_shell.rs:53` 的重试条件是 `== "dirty"`。保存失败后状态为 `"error"`，于是**自动保存循环永久停摆**，且没有持久告警 —— 磁盘满、权限问题、数据库被锁都会走到这个状态。

**修正动作**

```rust
    // 后台自动保存：dirty 或上次失败（error）时保存；失败做指数退避，连续失败提示用户
    Effect::new(move |_| {
        let ctx = app_ctx;
        leptos::task::spawn_local(async move {
            let mut failures: u32 = 0;
            loop {
                let base = ctx.auto_save_interval.get().max(5);
                let wait = base.saturating_mul(1u32 << failures.min(3)).min(60);
                TimeoutFuture::new(wait * 1000).await;

                match ctx.save_status.get().as_str() {
                    "dirty" | "error" => {
                        perform_save(ctx);
                        // 保存是异步的，等一拍再读结果
                        TimeoutFuture::new(1500).await;
                        if ctx.save_status.get() == "error" {
                            failures += 1;
                            if failures == 3 {
                                ctx.save_alert.set(Some(
                                    "自动保存已连续失败，请检查磁盘空间后手动保存（⌘S）".into(),
                                ));
                            }
                        } else {
                            failures = 0;
                        }
                    }
                    _ => failures = 0,
                }
            }
        });
    });
```

配套：`AppContext` 新增 `pub save_alert: RwSignal<Option<String>>`；`status_bar.rs` 在 `save_alert` 非空时常驻显示红色提示（当前 `save_status == "error"` 只在按钮上体现，容易被忽略）。

**实现备注（复核时补充）**：

- 循环里的 `ctx.auto_save_interval.get()` 是在 `spawn_local` 内的**非响应式读取** —— 信号变化不会触发 Effect 重跑，只是循环每拍轮询时取到新值。行为可用，但请显式注释这是"轮询语义"，避免后人误以为改设置会立即生效或误解为响应式绑定。
- `perform_save` 之后固定 `TimeoutFuture::new(1500)` "等一拍"是硬编码时序：保存耗时超过 1.5s 时会误判为失败并累加 `failures`。更稳的做法是让 `perform_save` 返回一个可 `await` 的完成信号（如 `oneshot` 或把状态判定挪进保存回调本身），把"保存完成"从猜测变成事件。

**验收**：把应用数据目录的 `easy-writing.db` 设为只读（`chmod 444`），输入若干文字后等待两个自动保存周期，必须出现红色常驻提示且状态栏显示重试中；恢复权限后应自动恢复为已保存。

> `impl<'de, R: Runtime> CommandArg<'de, R> for AppHandle<R>`，但漏看了约束：**R 必须与注册时的 Runtime 相同**。
> 而命令声明的是 `tauri::AppHandle`，即 `AppHandle<Wry>`，因此它不满足 `CommandArg<MockRuntime>`。
> 把 `save_chapter_content` 加进 `mock_builder()` 的 `generate_handler!` 后，编译直接报错：
>

>   the trait `serde_core::de::Deserialize<'_>` is not implemented for `AppHandle`
>   = note: required for `AppHandle` to implement `CommandArg<'_, MockRuntime>`
> ```
>
> 所以正确结论是：**只要该命令的首参还是 `tauri::AppHandle`，就不可能被 MockRuntime 用例覆盖**，
> 这正是 `command_key_sweep.rs` / `ipc_argcase.rs` 把它排除在外的原因。

>   * 写入路径覆盖到数据层，读取路径仍走真实 IPC；

### P1-4 数据库迁移版本化

**证据**：

- `src-tauri/migrations/` **只有** `V001__init.sql` 一个文件，没有版本号表、没有迁移阶梯。
- `src-tauri/src/db/mod.rs:57-58` 每次启动都全量 `execute_batch(include_str!("../../migrations/V001__init.sql"))`，靠 `IF NOT EXISTS` 幂等。
- `src-tauri/src/db/mod.rs:61-86` 是散落的 `ALTER TABLE ... ADD COLUMN` / `CREATE TABLE IF NOT EXISTS`，**全部 `let _ = ` 忽略错误**。加列失败（列已存在、磁盘只读、被锁）与"已是最新"无法区分。

**修正动作**

1. 新增 `schema_version` 表：

```sql
CREATE TABLE IF NOT EXISTS schema_version (
    version     INTEGER PRIMARY KEY,
    applied_at  TEXT NOT NULL DEFAULT (datetime('now'))
);
```

2. 把 `mod.rs` 里散落的 ALTER/CREATE 收进编号迁移文件 `V002__chat_and_relations.sql`、`V003__...`，`init_db` 改为版本驱动：

```rust
const MIGRATIONS: &[(i64, &str)] = &[
    (1, include_str!("../../migrations/V001__init.sql")),
    (2, include_str!("../../migrations/V002__chat_and_relations.sql")),
    (3, include_str!("../../migrations/V003__schema_version.sql")),
];

pub fn init_db(app_data_dir: PathBuf) -> Result<DbPool, Box<dyn std::error::Error>> {
    // ... 建池不变 ...
    let mut conn = pool.get()?;
    conn.execute_batch(MIGRATIONS[0].1)?;  // V001 保持幂等，兼容既有库
    conn.execute_batch("CREATE TABLE IF NOT EXISTS schema_version (version INTEGER PRIMARY KEY, applied_at TEXT NOT NULL DEFAULT (datetime('now')));")?;

    let mut applied: i64 = conn.query_row("SELECT COALESCE(MAX(version), 0) FROM schema_version", [], |r| r.get(0))?;
    for (version, sql) in MIGRATIONS {
        if *version <= applied { continue; }
        let tx = conn.transaction()?;            // 每步一个事务，失败可回滚
        tx.execute_batch(sql)?;                  // 不再 let _ =
        tx.execute("INSERT INTO schema_version (version) VALUES (?1)", [version])?;
        tx.commit()?;
        applied = *version;
    }
    Ok(pool)
}
```

> **实现备注（复核时补充）**：上面这段示例代码先 `execute_batch(MIGRATIONS[0].1)` 再建 `schema_version` 表，随后循环从 `applied = 0` 起，会把 V001 **再执行一遍**并插入版本 1。因为 V001 本身幂等（`IF NOT EXISTS`）所以能工作，但这依赖幂等性这一隐含前提 —— 实现时请显式注释，或干脆让循环从版本 2 开始（V001 已在前面单独执行过）。这与现状"每次启动全量重跑 V001"的行为保持一致，不算回退。
>
> **落地时的处理方式**：最终实现没有照抄上面这段示例循环。`init_db` 里 V001 由
> `if applied < 1 { ... }` 显式把关，只在**首次**执行，不存在「回头再跑一遍 V001」的情况；
> 版本写入用 `INSERT OR IGNORE`，因此两个实例并发首启也不会因主键冲突启动失败。
> 示例代码保留在此仅作设计说明。

3. 对"列已存在"这类**预期内**的错误做显式白名单判断，而不是笼统吞掉：

```rust
fn is_duplicate_column(e: &rusqlite::Error) -> bool {
    matches!(e, rusqlite::Error::SqliteFailure(_, Some(msg)) if msg.contains("duplicate column name"))
}
```

**验收**：新增 `src-tauri/tests/migration_ladder.rs`

- 用 V001 建库 → 插一条 novel → 跑 `init_db` → 断言数据仍在、`schema_version` 为最新；
- 重复跑三次 `init_db`，断言不报错且版本号不增长；
- 构造一个只有 V001 的旧库（缺少 `chat_session.title` 等列），断言升级后列存在。

### P2-6 弱类型 bridge 收敛（低优先，但便宜）

## 附带修正（与主问题无关，但同一批改掉更省事）

1. **`packageManager` 缺失导致工具链不可复现**：`package.json` 没有 `packageManager` / `engines` 字段；本机 pnpm 为 **12.6.0**，`release.yml` 固定 pnpm **9**，lockfile 为 `lockfileVersion: '9.0'`。三者不一致会让"本地能装、CI 装出不同结果"变得可能。

```diff
   "private": true,
+  "packageManager": "pnpm@9.15.0",
+  "engines": { "node": ">=20" },
```

> **执行时的重要发现：绝对不要为了消除 pnpm 10+ 的 build-script 审批提示而新增 `pnpm-workspace.yaml`。**
>
> pnpm 12 在本仓库跑 `install` 时会自动生成一个 `pnpm-workspace.yaml`（内容形如
> `allowBuilds:\n  esbuild: set this to true or false`），并让 `pnpm install` 以
> `ERR_PNPM_IGNORED_BUILDS` 失败。看着很像是"补个配置就好"，但这个仓库**已经踩过一次**：
>
> ```
> 33dffdb fix(ci): remove invalid pnpm-workspace.yaml to resolve CI pnpm install error
>   -allowBuilds:
>   -  esbuild: true
> ```
>
> 上一版加了 `allowBuilds: esbuild: true`，直接导致 CI 的 `pnpm install` 失败，只能回滚。
> 原因是 pnpm 9（CI 用的版本）并不支持这个字段，而 `pnpm-workspace.yaml` 本身又会让 pnpm
> 把该目录当成 workspace 根，语义随之改变。
>
> **正确做法就是本方案写的：用 `packageManager` 把版本钉到 9.15.0**，让本地和 CI 用同一个 pnpm；
> pnpm 10+ 用户如果确实需要，自己在本机跑 `pnpm approve-builds`，不要提交 workspace 配置文件。
> 执行过程中 pnpm 12 自动生成的那个文件已从工作区删除。

2. ~~**仓库注释与实际不符**~~ —— **已实测推翻，原注释是对的**。

   我在方案里断言 `src-tauri/tests/command_key_sweep.rs:221-225` 与 `ipc_argcase.rs:113-115` 的注释过期，
   依据是 `tauri-2.12.3/src/app.rs:487` 存在 `impl<'de, R: Runtime> CommandArg<'de, R> for AppHandle<R>`。
   但该实现的 `R` 必须与注册时的 Runtime 相同，而命令声明的是 `tauri::AppHandle` = `AppHandle<Wry>`，
   因此不满足 `CommandArg<MockRuntime>`。把 `save_chapter_content` 注册进 mock 后编译报错 E0277。

   **结论：这两处注释准确，不要修改，也不要再尝试把该命令接进 MockRuntime 用例。**
   想真正覆盖 IPC 写入路径，前提是把 `AppHandle` 从该命令上摘掉（行为改动）。
