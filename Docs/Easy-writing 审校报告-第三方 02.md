
P1：AI 提炼失败保护还没有覆盖整个处理链路
文件：extraction.rs
这是我认为目前最值得继续完善的 AI 数据一致性问题。
当前流程大致如下：
调用四个 Agent

解析模型输出，查询去重记录，写入候选

根据 all_succeeded 决定是否写入 extracted_hash


问题在于，目前 all_succeeded 主要反映 Agent 任务是否正常返回，而没有完整反映候选数据是否成功处理。
例如：
- 模型正常返回 HTTP 结果，但输出无法被解析，解析函数最终返回空候选列表。
- 查询候选是否重复时，数据库操作失败。
- insert_candidate 写入失败，错误被忽略。
从当前代码来看，这些路径不一定会把 all_succeeded 改成 false，最终仍可能更新 extracted_hash。

这里有一个重要区别：模型明确返回合法空数组 []，可能代表确实没有可提炼的内容；不能把它简单判定为失败。但格式解析失败与合法空结果必须明确区分。

- 只有四个 Agent 的输出均得到有效处理，且应入库的候选全部成功保存后，才能将章节标记为完成。
- 增加数据库写入失败与异常 JSON 输出的回归测试。
P1：异步读取目标章节期间，仍需要防止新的输入进入旧编辑器
文件：chapter_list.rs
目前 request_switch_chapter 会先检查保存状态。如果状态已经是 saved，就启动异步的 do_switch_chapter。
do_switch_chapter 随后通过 IPC 读取目标章节，收到结果后再将正文设置到编辑器中。在这段等待期间，当前章节仍未完成界面切换。

GitHub



这就留下一个很窄的竞态窗口：
1. 用户点击另一个章节时，原章节状态是 saved。
2. 程序开始异步读取目标章节。
3. 在目标章节返回前，用户又在当前编辑器中输入文字。
4. 目标章节加载完成后，程序调用 set_content 替换编辑器内容。
如果这个窗口内的输入还未保存，理论上仍可能被覆盖。
本地数据库读取通常很快，因此这不是我能确认已经发生的数据丢失事故，而是当前控制流中尚未完全封闭的风险。
建议： 点击切章后立即锁定编辑器输入，直到目标章节加载完成；或者在目标章节真正写入编辑器之前，重新检查 edit_seq 和保存状态，如果期间发生了新输入，就取消切换并提示用户保存。
P2：删除章节时，数据库失败可能导致界面误删条目
文件：chapter_list.rs
当前 delete_chapter_by_id 中有一段值得修改的逻辑：它忽略 delete_chapter 的执行结果，之后仍然从本地章节列表中移除该章节。

GitHub



如果数据库删除失败，界面可能先隐藏这一章，但重新打开作品或重新加载列表后，这一章又会出现。
更合理的处理应当是：
- 先等待删除命令返回结果。
- 成功后再移除界面条目。
- 失败时保留条目，并明确提示原因。
- 如果被删除的是当前章节，额外确认未保存内容如何处理。
这不一定会导致永久数据丢失，但会造成界面状态和数据库状态不一致，并增加用户误操作的风险。
P2：CSP 已经补上，但限制还不够严格
文件：tauri.conf.json
之前的 csp: null 已经改为具体策略，这是正确的方向。但当前策略依然允许：
- script-src 使用 'unsafe-inline'。
- connect-src 连接任意 HTTPS 来源。
- 图片也允许任意 HTTPS 来源。
  
  GitHub
考虑到软件支持自定义模型服务商，允许多个远程接口访问可能有现实原因；但这也意味着 CSP 仍提供较宽的网络连接权限。
建议重新核对哪些网络请求必须由 WebView 发起。对 AI 推理和 WebDAV 等可由 Rust 后端处理的请求，尽可能避免让前端拥有不必要的远端连接能力；对脚本、图片和网络来源采用能满足功能的最小范围。
