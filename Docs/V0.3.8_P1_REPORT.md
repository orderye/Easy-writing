## 1. P1-2 AI 提炼可观测性（对应 C-06 / C-07）

### 1.1 本次修复的最高价值缺陷

基线 C-06：`run_parallel_extraction` 在所有 Agent 失败时仍返回
`Ok(vec![])`。**API Key 失效、限流、断网全部显示为「本章没有新设定」。**
作者会认为模型确认本章无新内容，因此永远不会去检查配置 ——
一个配置错误可以静默半年，直到某天发现整本书没有提炼过任何东西。

### 1.2 新的结果模型

新增 `src-tauri/src/agent/outcome.rs`：

```rust
ExtractionOutcome {
    candidates: Vec<ExtractionCandidate>,
    succeeded_agents: usize,
    failures: Vec<AgentFailure>,      // 已脱敏，不含正文与密钥
    skipped_fingerprint_match: bool,
    all_succeeded: bool,
}
```

`is_failure()` 让「没有提炼到东西」与「提炼失败」成为两种可区分的结果；
`summarize()` 产出面向作者的一句话，明确告知**该做什么动作**。

### 1.3 错误分类（7 类）

`ExtractionFailureKind`：`Network` / `Auth` / `RateLimited` / `Timeout` /
`MalformedOutput` / `Database` / `Cancelled` / `Internal`。

每个类别配 `user_hint()`（告诉作者该做什么）与 `is_retryable()`。

`classify_error()` 目前是**启发式文本匹配**，不是结构化解析。原因：
上游 `openai.rs` / `anthropic.rs` 仍返回裸 `String`，改它们的返回类型会
波及 chat / polish / consistency / models 等全部调用点，
超出可靠性专项的「最小必要修改」边界。这一点在代码注释里写明了，
并标注了后续升级路径。

这个取舍是有代价的：**厂商改了错误文案，分类就会失准**。
因此 `Internal` 兜底时给的是通用建议，而不会假装知道原因。

### 1.4 顺带修复的两个相关缺陷

1. **指纹命中时返回全作品候选**。旧实现在 `extracted_hash` 命中时返回
   `list_pending_candidates(novel_id)` —— 那是**整部作品**的待审候选，
   不是本章的，却作为「本次提炼结果」展示给作者。
   现在用 `skipped_fingerprint_match: true` 显式标记。

2. **自动提炼失败无痕迹**。后台自动提炼路径（`should_trigger_auto_extract`）
   只 emit 了候选数。现在失败时会 `eprintln!` 汇总原因 ——
   作者不在弹窗前，这是他唯一能看到的信号。

### 1.5 前端同步修改

`extraction_modal.rs` 增加红色告警条，区分：
- 提炼失败（显示具体是哪些 Agent、什么类别、该做什么）；
- 提炼成功但无新增（正常状态，不告警）。

**这是本次唯一触及前端的 P1 改动**，因为「失败必须可见」这件事
在后端无法独立成立。

### 1.6 未做（明确标记）

- **无持久化任务记录**。没有新增任务表。理由：当前 IPC 是一次性调用，
  没有「任务可恢复 / 可查询」的真实需求，任务书也明确要求
  「不要为了追求完整架构而过度设计」。
- **无取消机制**。全仓库无 `cancel` / `AtomicBool` / 句柄注册。
  4 个 Agent 是 detach 的 `tokio::spawn`，用户点关闭只是隐藏弹窗，
  后端继续跑完。
- **无自动重试**。重试依赖用户手动点「重新提炼」。
  但重试是幂等的：`dedup_key` 三种算法（create / update / chapter_summary）
  覆盖了重复插入，因此「重试不会产生重复候选」这一点有测试保证。

## 2. P1-3 安全与敏感数据治理（对应 C-08 / C-10）

### 2.1 日志脱敏（C-08）

原实现把模型返回的**前 150 个字符**拼进解析错误消息，而模型输出中包含候选的
`evidence` 字段 —— 那是**直接从作者正文摘录的原句**。这条错误一路传到
`eprintln!`，等于把小说正文片段写进普通日志。

修复：
- `extraction.rs` 的错误消息改为「输出长度 + 脱敏片段」，
  脱敏由 `redact_prose_fragment()` 完成 —— 只保留 ASCII 结构性符号
  （`{` `[` `"` 等），其余一律替换为 `·`。排障时仍能看出「是不是 JSON」，
  却拿不到任何正文。
- 新增 `sanitize_reason()`：只保留 HTTP 状态码这一项确定安全的信息，
  **丢弃厂商返回的完整响应体**（某些厂商会在错误里回显请求摘要）。

顺带把三处日志里的 `item.title`（模型产出的实体名）也去掉。

**未发现 API Key 曾被打印** —— 这一点在基线审计中已确认，实现保持不变。

### 2.2 外链 host 限制（C-10）

`open_external_url` 原来只校验 `http(s)://` 前缀。传入
`http://169.254.169.254/latest/meta-data/` 即可让系统浏览器访问云元数据端点。

新增拦截：回环地址、`localhost`、私有网段（10/8、172.16/12、192.168/16）、
链路本地（169.254/16）、组播、`::1`、以及
`metadata.google.internal`。放行一切正常公网地址。

这让 `open_external_url` 与 `ai/gateway.rs` 的 `validate_base_url`
（仅允许 localhost / 私有网段走明文 HTTP）在策略上保持一致 ——
之前是两套不同的标准。

### 2.3 凭据生命周期审计结论

- WebDAV 密码：存系统钥匙串（`keyring.rs`），数据库只存 `pwd_ref`。
- API Key：`llm_profile.key_ref` 存钥匙串引用。新增测试
  `llm_profile_key_is_stored_as_reference_not_plaintext` 守住这一点。
- **钥匙串不可用时会直接报错**（`map_err`），**不会降级为明文存储** ——
  这一点实现是正确的，基线审计已确认，本次未改动。
- 新增 `backup_manifest_contains_no_credentials`：造出含真实形状凭据的库，
  断言备份清单不含 key / url / pwd_ref / username。

### 2.4 未做（明确标记）

- **无结构化日志框架**。仓库没有 `tracing` / `log`。
  本次仍用 `eprintln!`，只约束其内容格式。引入日志框架属于架构变更，
  超出本次范围。
- **无 capabilities 权限白名单**。仓库不存在 `src-tauri/capabilities/`，
  所有 `generate_handler!` 注册的命令对前端一律开放。
  Tauri 2 支持按能力收敛，但这是配置层的结构性变更，需要逐命令评估，
  不宜在可靠性专项里顺手做。
- **依赖漏洞扫描未接入 CI**。仓库未使用 `cargo-audit` / `npm audit`。
  需要先跑一次真实扫描拿到基线，再决定是否设门禁 ——
  盲目设门禁会让 CI 因存量漏洞直接变红。
- macOS / Windows 签名未配置（见 P0 报告 3.3）。

## 3. P1-4 导入边界（对应 C-09）

### 3.1 EPUB 四层上限

新增四道限制，全部在 `import/epub.rs`：

| 限制 | 阈值 | 位置 |
|---|---|---|
| 文件入口体积 | 64 MiB | `parse_import_epub` 开头，base64 解码后 |
| 归档条目数 | 20 000 | 遍历前 |
| 声明解压总体积 | 512 MiB | 遍历前 |
| **单条目解压体积** | 16 MiB | **读取时逐块计数** |

最后一道是关键：`zip` 头里的 `uncompressed_size` **可以被伪造**，
因此真正的兜底必须在实际读取过程中计数。`read_entry_text()` 取代了
全部 7 处无上限的 `read_to_string`。

### 3.2 TXT 导入：审计后未改动

`import/text.rs` 的路径读取的是用户自己选中的本地文件，
不是「任意远端数据」。编码识别失败时返回错误而非静默乱码。
本次未发现需要修改的问题，因此未改动。

### 3.3 新增测试（`epub_import.rs`，5 个）

| 测试 | 覆盖 |
|---|---|
| `rejects_oversized_epub_payload` | 入口体积上限 |
| `rejects_non_zip_payload_with_clear_message` | HTML 错误页误当 EPUB |
| `rejects_zip_bomb_entry` | 48 MiB 条目（压缩后仅数十 KB） |
| `rejects_zip_with_too_many_entries` | 20 050 条目 |
| `normal_epub_still_imports_after_limits_were_added` | **加了上限不能误伤正常文件** |

最后一条是这组测试存在的意义：只测「能拒绝」而不测「不误伤」，
就很容易在某个合理的 EPUB 上把导入功能弄坏。

### 3.4 已知未覆盖

- EPUB 内部的路径穿越（`href="../../etc/passwd"`）：**当前实现不把 EPUB 内的
  文件写到磁盘**（只读出文本入库），因此不存在路径穿越写入风险。
  但未做显式断言来钉住这个前提 —— 若将来改为落盘，这里会成为真实漏洞。
- 超大合法 EPUB（100 MiB 全插图小说）会被 64 MiB 上限拒绝。
  这是**有意的取舍**：桌面应用拒绝 100 MiB 的单文件导入是可接受的，
  且错误信息明确说明了原因。

## 4. P1-1 性能基准（对应 C-12）

### 4.1 新增 `src-tauri/tests/perf_benchmark.rs`

5 个基准用例，全部标记 `#[ignore]`（默认不随 `cargo test` 运行）：

| 用例 | 数据规模 |
|---|---|
| `perf_small_novel_baseline` | 2 卷 25 章 × 2000 字 |
| `perf_hundreds_of_chapters_baseline` | 12 卷 × 30 章 × 3000 字（约 360 章） |
| `perf_thousand_chapter_long_paragraph_baseline` | 50 卷 × 20 章 × 4000 字（1000 章） |
| `perf_fulltext_search_baseline` | 30 卷 × 20 章，搜索词全命中/零命中 |
| `perf_many_assets_baseline` | 200 张图片 + 存储对账 |
| `perf_scaling_report` | 4 档规模，量化「每章耗时」是否随规模上升 |

**数据集是合成的**，代码注释与输出都显式声明「合成数据，非真实用户作品」。
不得把它当作真实作品性能证据。

### 4.2 `perf_scaling_report` 的价值

它回答的不是「绝对耗时」，而是一个可证伪的问题：
**章节目录加载是否随章节数线性增长？**

如果某次改动引入了「每章一次查询」这类 N+1，「每章(µs)」会从常数
变成递增。这个指标比绝对毫秒数更能抓住真正的回归。

### 4.3 CI 门禁：已接入，阈值刻意宽松

通过环境变量 `EW_PERF_GATE_MS` 打开阈值判定，`ci.yml` 中新增
`performance` job 并设为 **500 ms**。

**为什么是 500 ms 而不是更紧**：CI runner 的 CPU 与开发机差异很大，
而我们**从未在 runner 上采集过真实分布**。凭开发机数据拍一个紧阈值，
只会得到一个天天误报、最终被所有人忽略的假门槛 ——
那比没有门槛更糟，因为它会训练团队「红色构建是正常的」。

500 ms 这个值只用于拦截「劣化一个数量级」的回归
（例如误引入 N+1 导致的 20~50 倍劣化），对当前实测值
（最慢 48 ms）有 10 倍余量，因此不会误报。

**待改进**：应在 CI runner 上跑几轮收集真实分布，再把阈值收紧到
实测 P95 的 2~3 倍。这是一个明确的后续动作，不是「已完成」。

### 4.4 尚未测量的项

任务书 P1-1 任务 B 列出的以下操作**未测量**，因为需要浏览器环境
（本次无头，无 GUI）：

- 应用启动及作品列表加载（端到端）
- 章节切换（含前端 `edit_seq` 校验链路）
- 连续输入时的响应、自动保存延迟
- 图片图库浏览（渲染侧）
- 长时间编辑后的内存变化

Rust 侧已覆盖的是：目录加载、单章打开、单章保存、字数统计、全书搜索、
图库列表、存储对账。

### 4.5 实测基线（2026-10-19，macOS arm64 / 外置机械盘）

```
$ cargo test -p easy-writing-core --test perf_benchmark -- --ignored --nocapture
test result: ok. 6 passed; 0 failed
```

| 操作 | 数据规模 | 耗时 |
|---|---|---|
| 作品章节目录加载 | 50 章 | 0.14 ms |
| 作品章节目录加载 | 360 章 | 1.94 ms |
| 作品章节目录加载 | 1000 章 × 4000 字 | 7.05 ms |
| 打开单章正文 | 50 章 | 0.18 ms |
| 打开单章正文（4000 字） | 1000 章 | 0.07 ms |
| 保存单章（自动保存路径） | 1000 章 | 0.06 ms |
| 全书字数统计 | 360 章 | 1.16 ms |
| 全书字数统计 | 1000 章 | 4.87 ms |
| 全书搜索（全命中，最坏情况） | 600 章 | **48.20 ms**（首次，含缓存冷启动）／后续 12.03–12.58 ms |
| 全书搜索（零命中） | 600 章 | 11.92 ms |
| 图库资产列表 | 200 张图 | 0.91 ms |
| 存储对账（孤儿文件扫描） | 200 张图 | 1.52 ms |

**规模效应（章节目录加载）**：

| 章节数 | 耗时 (ms) | 每章 (µs) |
|---|---|---|
| 50 | 0.229 | 4.57 |
| 200 | 0.508 | 2.54 |
| 400 | 0.822 | 2.06 |
| 1000 | 2.688 | 2.69 |

**结论：每章耗时在 2.0–2.7 µs 之间基本持平，没有随规模上升的迹象 ——
说明目录加载是单次批量查询，不存在 N+1。** 这正是这个指标要抓的东西；
本次测量结果为「干净」。

（50 章那一档的 4.57 µs 偏高是预热不足，不是规模效应 ——
50/200/400 三档呈下降趋势本身就说明不是线性增长。）

**全书搜索是唯一显著的高成本操作**：600 章、词条全命中时达 48 ms
（冷启动），后续查询约 12 ms。相比之下同规模下目录加载只要 2 ms。
原因是 `LIKE '%term%'` 前置通配符无法走索引，必须全表扫描 + 在 Rust 侧
数出现次数并截取上下文。对长篇作者而言这是反复执行的操作，
是 P1-1 任务 D 明确的优化方向。

**重要说明**：以上全部为**合成数据**（代码与输出中已标注）。
绝对数值不能代表真实用户作品的性能，只能作为**同环境下的回归对照**。

### 4.6 定位到的高成本操作

基线代码审查中已确认两处**结构性**性能问题，本次未修改（需要 UI 侧配合，
超出可靠性专项范围）：

1. `find_chapters_mentioning` 使用 `LIKE '%' || ?2 || '%'` ——
   前置通配符使 SQLite 无法使用索引，只能全表扫描。
   章节量级下可接受（该函数注释里已说明），但在千章级会线性劣化。
   `perf_fulltext_search_baseline` 已把它纳入基线，可在优化前后直接对比。

2. 资产引用检查 `count_like` 使用 `LIKE '%<hash>%'` 扫描 `chapter.content`
   与 `chapter_revision.content`（`asset.rs:220-225`）。
   每次删除图片前都要做一次，长篇作品下代价不低。
   仓库已建立「按 hash 匹配而非按 rel_path」的判断（因为 URL 会被百分号编码），
   但没有避免全表扫描。
