# 二、P0：发布阻断任务

## P0-1：恢复流程真正下载并校验远端备份清单

### 当前代码依据

重点位置：

- `src-tauri/src/sync/restore.rs`：`run_consistency_restore`。
- `src-tauri/src/sync/backup.rs`：`cross_check_manifest`、`preflight_backup`。
- `src-tauri/src/sync/manifest.rs`：`BackupManifest`、`read_sidecar`、`sidecar_path_for`、`sha256_hex`。

当前恢复流程下载 `.db.gz`，解压到临时数据库并执行预检；但在调用 `cross_check_manifest` 前，没有看到下载对应的远端 `.db.gz.json` 文件并放置到该函数可读取的位置。现有交叉校验也只比较作品数、章节数，差异仅作为提示。详见当前源码：`restore.rs`、`backup.rs` 与 `manifest.rs`。 

### 目标

让恢复流程能够区分三种情况：

1. **存在有效清单：** 下载并验证清单，对备份执行真实交叉校验。
2. **历史备份没有清单：** 允许走兼容路径，但明确告知用户这是无清单的旧备份。
3. **清单存在但损坏、不兼容或与备份不匹配：** 不得静默退化成“无清单历史备份”，不得在未确认安全前覆盖当前数据库。

### 实施要求

#### A. 先核对 WebDAV 现有接口

阅读 `src-tauri/src/sync/webdav.rs` 和 `restore.rs` 中的实际调用方式，复用已有的下载、列举、文件大小查询等能力。

不得臆造诸如 `download_manifest()`、`get_backup_hash()` 等现有接口。如果需要新能力，必须先确认已有客户端方法不足，再实现最小必要扩展。

#### B. 下载正确的清单文件

依据现有命名规则，备份文件：

`backup_时间戳.db.gz`

对应清单：

`backup_时间戳.db.gz.json`

具体远端路径必须通过当前的路径拼接逻辑生成，不能让用户输入的文件名或远端返回的路径绕过已有文件名校验。

将清单解析为现有 `BackupManifest` 结构，不要另建字段重复、含义冲突的清单类型。

#### C. 校验清单与数据库的一致性

至少检查以下项目：

- `manifest_version` 是否属于当前客户端支持的清单格式。
- `schema_version` 是否与备份实际 schema 版本一致。
- 清单声明的作品、卷、章节等实体数量是否与数据库实际数量一致。
- 对当前清单包含的其他实体计数，逐项检查数据库实际值，而不只检查作品数和章节数。
- 清单声明的压缩文件大小与实际下载字节数是否一致。
- 对清单记录的图片资产，校验相对路径是否合法、资产是否存在，以及文件大小和 SHA-256 是否符合清单。
- 清单字段缺失、负数计数、重复资产路径、非法相对路径或无效哈希格式必须得到明确处理。
- 对数据库内部资产记录与清单资产列表的差异，产生可追踪的校验结果。

清单中的资产路径必须限制在应用资产目录内。不得直接信任远端清单中的绝对路径或 `../` 路径。

**重要：** 当前 `manifest.rs` 的 `reconcile_with_disk` 会在文件缺失时从清单中剔除资产；修复时必须检查这个行为是否会让备份生成阶段掩盖缺图。不得只校验最终清单，而忽略原始数据库记录中已经存在但本地文件缺失的资产。

#### D. 修正清单生成的错误处理

当前 `manifest.rs` 中的 `build_manifest` 会对部分查询使用 `unwrap_or(0)`，而 `collect_assets` 也可能将查询失败转成空列表。

改为明确的错误传播：

- schema 版本读取失败：备份清单生成失败。
- 必须统计的表读取失败：备份清单生成失败。
- 资产表无法读取：明确报错或通过结构化结果表示失败，不得伪装成“没有资产”。
- 单个物理文件确实缺失：按设计生成明确的缺失资产报告，不得与数据库查询失败混为一谈。

具体函数签名应结合现有调用链决定；修改后必须同步修复所有调用方，不得使用大量 `unwrap_or_default()` 掩盖错误。

#### E. 处理历史备份兼容性

- 清单文件不存在：保留历史无清单备份的兼容能力。
- 清单文件存在但 JSON 损坏：返回明确错误，不得当成清单不存在。
- 远端清单下载失败且无法确定是 404 还是网络错误：不得直接认定为历史备份。
- 只有确认服务端返回的确实是“文件不存在”，才可以进入历史备份兼容分支。
- 对没有清单的旧备份，仍须执行现有 SQLite 完整性检查、schema 检查和解压大小限制。

#### F. 调整恢复调用顺序

推荐顺序：

1. 校验远端备份文件名。
2. 下载备份文件。
3. 下载或确认清单是否存在。
4. 解压至独立临时文件。
5. 执行 SQLite 完整性与 schema 预检。
6. 校验清单及资产。
7. 向前端返回恢复预检结果。
8. 用户确认后，才允许进入数据库覆盖阶段。

如果现有架构无法一次完成上述流程，应拆分为“预检”和“执行恢复”两个阶段，但必须沿用真实 IPC / Tauri command 架构，不得绕过现有权限或错误处理机制。

### 必须新增的测试

优先扩展 `src-tauri/tests/backup_integrity.rs`；如需 WebDAV 交互测试，另建独立测试文件。

| 测试 | 预期结果 |
|---|---|
| 有效数据库 + 有效清单 | 清单成功读取，计数与资产校验通过 |
| 清单作品数被篡改 | 校验失败，不覆盖现有数据库 |
| 清单章节数被篡改 | 校验失败，不覆盖现有数据库 |
| 清单中其他实体数量被篡改 | 对应校验失败 |
| 清单压缩大小不匹配 | 校验失败 |
| 图片内容与清单哈希不匹配 | 校验失败或进入明确的可见修复流程；不得静默成功 |
| 清单 JSON 损坏 | 明确报错，不得退化成旧备份 |
| 清单版本不支持 | 明确拒绝或进入受控兼容处理，不得忽略版本 |
| 清单不存在的历史备份 | 按旧格式路径进行 SQLite 预检 |
| 清单包含 `../` 路径 | 拒绝该路径，不能读写应用目录之外的文件 |
| 清单中重复资产路径 | 检测并报告 |
| schema 统计查询失败 | 清单生成失败，不得生成伪造的零计数清单 |

### 验收标准

- 新格式备份恢复时，确实读取对应的远端 JSON 清单。
- 清单与数据库不一致时，恢复流程不会覆盖当前数据库。
- 历史无清单备份仍可通过现有安全预检。
- 损坏清单与缺失清单可以被明确区分。
- 不存在通过默认值掩盖清单关键字段读取失败的路径。
- 全部新增测试通过，原有测试无回归。

## P0-2：恢复失败必须具备真实、可验证的回滚机制

### 当前代码依据

文件：`src-tauri/src/sync/restore.rs`。

当前函数在恢复前使用 SQLite Backup API 创建 `pre_restore_*.db` 安全快照；之后使用另一个 SQLite Backup API 将临时备份写入目标数据库。但目标数据库写入失败时，没有看到明确的恢复快照回滚流程。后续本地配置写入也存在忽略 SQL 错误的情况。见当前源码的 `run_consistency_restore` 及其配置恢复部分。

### 目标

恢复过程必须有明确的提交边界和失败策略。任何发生在数据库替换之后、且会导致恢复状态不完整的关键错误，都必须：

- 触发可靠回滚；或
- 让恢复进入明确的“部分恢复”状态，保留安全快照，并提供可执行的恢复路径。

不能在数据库只恢复了一部分时返回普通成功。

### 实施要求

#### A. 明确恢复事务状态

在 `restore.rs` 中梳理所有阶段：

- 安全快照创建；
- 远端下载；
- 解压和数据库预检；
- 清单校验；
- 目标数据库覆盖；
- 本地 WebDAV 配置恢复；
- 本地界面设置恢复；
- 图片素材回填与哈希检查；
- 最终结果汇总。

为关键阶段建立明确的结果和错误处理，不得用单个 `Result` 成功返回掩盖中间阶段的失败。

#### B. 为数据库替换建立回滚

优先评估现有 SQLite Backup API、`DbPool` 连接管理和数据库路径管理的实际限制，再选择实现方式。

允许的方案包括：

- 先写入独立的候选数据库，校验后再提交；
- 在现有架构下覆盖数据库，但对所有失败分支明确从安全快照回滚；
- 其他具有等效数据安全保证的方案。

不得假定直接重命名 SQLite 数据库文件就是安全替换。必须检查 WAL、SHM、连接池中已有连接、数据库路径和应用正在运行的情况。

如果采用安全快照回滚：

1. 记录快照路径和有效性。
2. 数据库覆盖失败时，尝试从快照恢复原库。
3. 回滚失败时，保留快照，返回同时包含原始失败与回滚失败的信息。
4. 不得删除唯一可用的安全快照。
5. 在回滚完成前，不得将恢复报告标记为完整成功。

#### C. 本地配置恢复必须可见且可处理

当前代码在写入 `webdav_config` 和 `app_setting` 时使用忽略执行结果的方式。

必须调整为：

- 逐项处理 SQL 错误；
- 在必要时使用 SQLite 事务保证本地配置恢复的原子性；
- 配置恢复失败时返回具体阶段和原因；
- 明确选择回滚整个恢复，或报告数据库已恢复但本地配置未恢复；
- 不得悄悄忽略失败。

对于 WebDAV 配置，必须确保恢复后仍保留本机当前的连接配置，而不是误用远端数据库中的连接设置。不得将 WebDAV 密码或 Keychain 引用打印到日志中。

#### D. 图片回填失败必须进入恢复结果

当前实现会对部分图片恢复问题生成 `RestoreIssue`，但数据库已经覆盖后才执行图片回填。

必须明确区分：

- 数据库恢复成功且全部资产完整；
- 数据库恢复成功，但部分素材无法恢复；
- 数据库恢复失败并已回滚；
- 数据库恢复失败且回滚也失败。

如果图片缺失属于可恢复问题，必须显示明确警告和缺失列表；如果属于不可接受的完整性失败，则必须在提交前校验或设计可靠回滚。

不能把“数据库恢复成功”直接等同于“整个项目恢复成功”。

#### E. 临时文件和安全快照生命周期

- 临时数据库创建失败：不动现有库。
- 快照创建失败：不动现有库。
- 清单校验失败：不动现有库。
- 目标库替换失败：触发回滚。
- 配置恢复失败：执行预定的回滚或显式部分失败策略。
- 临时文件清理失败：记录警告，不得覆盖原始错误。
- 安全快照只有在恢复结果达到约定的成功状态后才允许清理。

### 必须新增的故障注入测试

在 `src-tauri/tests/backup_integrity.rs` 或新建专门的恢复测试文件中，使用临时数据库和可控故障注入。

至少覆盖：

1. 安全快照创建失败。
2. 目标数据库打开失败。
3. SQLite Backup API 初始化失败。
4. 目标库写入过程中失败。
5. 本地 WebDAV 配置恢复失败。
6. 本地 UI 设置恢复失败。
7. 图片下载失败。
8. 图片哈希不匹配。
9. 回滚成功。
10. 回滚本身失败。
11. 恢复进程在关键阶段中断后的恢复策略。

不得依赖真正把开发机磁盘写满来完成全部故障测试。可通过隔离文件系统、注入接口或受控失败点模拟，但必须确保测试验证的是实际恢复控制流，而不是仅测试一个独立的 mock。

### 验收标准

- 每个关键失败分支均有确定的结果状态。
- 数据库覆盖失败后，原始数据仍可读取，或系统明确保留可恢复快照并报告无法回滚。
- 配置恢复错误不再被吞掉。
- 回滚测试证明原数据库关键记录和数据计数保持不变。
- 测试失败时不会修改任何真实用户数据库。
- 所有测试通过后才能关闭本任务。

## P0-3：空库确认必须发生在覆盖现有数据库之前

### 当前代码依据

文件：`src-tauri/src/sync/restore.rs`。

当前流程在目标数据库写入之后才将空库状态加入恢复摘要。因此，用户无法在覆盖前基于预检结果明确确认是否要用空库覆盖现有作品。

### 目标

任何会用空库替换非空本地数据库的操作，都必须在覆盖发生前获得明确的用户确认。

### 实施要求

#### A. 前置预检

预检结果至少包含：

- 备份 schema 版本；
- 作品、卷、章节、字数统计；
- 是否为空库；
- 清单是否存在；
- 清单校验状态；
- 图片资产检查摘要；
- 备份是否通过 SQLite 完整性检查。

数据来源必须是已解压、已预检的候选备份，而不是远端文件名或未经验证的清单声明。

#### B. 追踪真实 UI 调用链

先定位触发 `run_consistency_restore` 的真实 Tauri command 和前端组件，再决定接口改造方式。

可以采用：

- 独立的预检 command 与确认后的恢复 command；
- 当前恢复流程返回预检信息，由前端确认后再执行；
- 与当前架构兼容的其他两阶段方案。

不得假设当前项目已经存在某个预检 command，也不得只增加一个未被前端调用的确认参数。

#### C. 确认条件

- 目标本地数据库非空，候选备份为空：必须明确二次确认。
- 目标本地数据库为空，候选备份为空：可以采用更简洁提示，但仍须展示实际恢复结果。
- 用户取消确认：不得覆盖本地数据库。
- 清单校验失败：不能仅凭用户点击“确认”绕过关键完整性校验。
- 历史无清单备份：明确告知缺少清单，但仍需通过 SQLite 预检。
- 前端确认后，如果候选备份已经改变或被重新下载，必须重新验证，不能确认 A 却恢复 B。

确认文案必须明确表达“将用空库替换当前已有作品数据”，不得使用含糊的“继续操作”。

### 必须新增的测试

- 非空库 + 空备份 + 用户取消：原库保持不变。
- 非空库 + 空备份 + 用户确认：只有在全部预检通过后才能执行恢复。
- 非空库 + 非空备份：不触发空库专属确认。
- 空库 + 空备份：恢复结果明确标识为空。
- 预检通过后候选备份改变：执行阶段必须重新校验。
- 清单损坏：不能由空库确认绕过。
- 前端确认流程与后端 command 契约一致。

### 验收标准

任何空库覆盖操作都在实际覆盖前完成确认。取消操作不得产生数据库、配置或素材变更。

# 三、P1：真实 WebDAV 集成测试

## P1-1：增加可重复运行的 WebDAV 端到端测试

### 当前代码依据

- `src-tauri/src/sync/webdav.rs`
- `src-tauri/src/sync/backup.rs`
- `src-tauri/src/sync/restore.rs`
- `src-tauri/tests/backup_integrity.rs`
- `.github/workflows/ci.yml`

项目现有报告明确指出：真实 WebDAV 服务端上的上传中断、远端 MOVE 失败、HEAD/文件大小检查等行为尚未完成集成验证。现有函数级测试不能替代真实 HTTP/WebDAV 行为验证。

### 目标

建立一个可自动启动、自动清理、可重复执行的 WebDAV 测试环境，覆盖真实 HTTP 请求、远端文件操作和备份恢复流程。

### 实施要求

#### A. 先核对 WebDAV 客户端的真实请求

阅读 `webdav.rs`，列出当前实际使用的方法和请求行为，例如：

- 文件列表；
- 文件上传与下载；
- 文件存在性查询；
- 文件大小查询；
- 远端 MOVE；
- 删除文件。

这些是待核对的现有行为清单，不是要求新增同名接口。最终测试必须根据实际实现编写。

#### B. 建立隔离服务端

优先使用能够在 CI 中启动、支持所需 WebDAV 方法的真实服务端容器。

可以评估 Nextcloud 或其他合适的 WebDAV 实现；选型需记录：

- 服务端版本；
- 容器镜像版本或固定标签；
- 支持的 HTTP/WebDAV 方法；
- 身份认证方式；
- 如何创建和销毁独立测试目录。

不得使用生产 WebDAV 账号或真实备份目录。

如果服务端镜像不支持某项测试所需能力，必须记录原因，不能通过跳过断言宣称通过。

#### C. 必测场景

| 场景 | 验收行为 |
|---|---|
| 上传数据库备份 | 远端文件内容可重新下载并通过预检 |
| 上传清单 | 对应 `.db.gz.json` 与备份文件正确匹配 |
| 下载备份和清单 | 恢复侧可以读取并校验清单 |
| 远端 MOVE 成功 | 临时文件按设计转为正式备份文件 |
| 远端 MOVE 失败 | 备份失败可见，不误报成功 |
| 上传中断或连接中断 | 不留下被当作完整备份的半成品 |
| 下载截断 | 恢复前预检拒绝该文件 |
| 文件大小校验失败 | 不将备份标记为已验证 |
| 服务端不支持或拒绝 HEAD | 按真实客户端策略处理，不能将未验证误报为验证通过 |
| 清单上传失败 | 用户或调用方能够获知清单缺失 |
| 远端图片缺失 | 恢复结果明确报告缺失资产 |
| 备份轮转 | 只删除允许轮转的文件，不能误删非备份文件 |
| 历史无清单备份 | 按兼容策略处理 |
| 错误凭据或无权限 | 明确失败，不得误报成功 |

#### D. 将关键测试接入 CI

在当前 `.github/workflows/ci.yml` 中增加独立的 WebDAV 集成测试 job 或步骤。

要求：

- 只对专用测试服务端和临时数据操作；
- 测试失败时保留脱敏日志；
- 服务端未启动、健康检查失败时明确失败；
- 只有明确标注为可选的外部服务测试才允许因缺少外部凭据跳过；
- CI 不依赖开发者个人机器上的 WebDAV 配置。

真实第三方服务的可选兼容性测试可以使用受控凭据运行，但不能成为唯一的 CI 验收证据。

### 验收标准

- CI 中有可重复运行的 WebDAV 集成测试。
- 至少一个真实 WebDAV 实现覆盖上传、下载、MOVE、清单读取和恢复。
- 关键失败路径有自动化测试。
- 测试数据不会进入真实用户的 WebDAV 目录。
- 集成测试报告包含服务端版本、测试数量、失败详情及退出码。

# 四、P1：历史 schema 连续迁移和大数据迁移验收

## P1-2：建立真实历史 schema 的连续升级测试

### 当前代码依据

- `src-tauri/tests/migration_ladder.rs`
- 数据库初始化与迁移实现：先搜索 `BASELINE_VERSION`、`schema_version` 及迁移函数，确认真实定义文件。
- `Docs/V0.3.8_P0_REPORT.md`

现有测试覆盖迁移幂等性及部分老库缺列场景，但尚未验证真实历史 schema 从 v1 连续迁移到当前 schema 的完整过程。

### 目标

证明用户从旧版本升级后，数据库可以按既有迁移阶梯逐级升级，不丢失核心业务数据，不跳过迁移，也不重复执行有副作用的迁移。

### 实施要求

#### A. 先确认真实迁移版本

Agent 必须先从代码中确认：

- 当前 `BASELINE_VERSION`；
- 实际存在的每个 migration 版本；
- 每个版本的 DDL / 数据转换；
- schema 版本记录方式；
- 应用启动时执行迁移的入口；
- 哪些历史字段和表已被后续版本删除或改名。

不得因为任务书示例写了 v1→v2→v3，就假定当前 schema 只存在三个版本。

如果当前 schema 确实是 v3，则测试 v1→v2→v3；如果实际版本不同，必须覆盖当前真实的完整迁移链。

#### B. 构造历史数据库 fixture

使用独立的测试数据库 fixture：

- 尽可能依据仓库历史迁移代码构造每个真实历史版本；
- 为关键表插入具有可识别值的测试记录；
- 覆盖作品、卷、章节、设定、角色、关系、章节版本、词库及其他当前真实业务表；
- 按实际 schema 选择有效字段，不臆造字段名称；
- 对历史版本不存在的表或字段，不得提前创建后再宣称测试了旧库升级。

优先使用 SQL fixture 或测试辅助函数；如果仓库存在历史数据库样本，先检查来源和许可，再决定是否使用。

#### C. 验证逐级迁移

每个历史版本至少验证：

1. 初始 schema 版本正确。
2. 每一级 migration 按预期执行。
3. 迁移结束后 schema 版本正确。
4. 关键表和索引存在。
5. 原有作品、卷、章节正文及其他业务记录保留。
6. 需要转换的数据内容符合迁移规则。
7. 重启或重复初始化不会重复执行迁移。
8. 中途失败时，不会将 schema 版本标记成已成功迁移。
9. 更高版本数据库不会被旧版本客户端擅自降级或覆盖。

具体断言根据实际 migration 逻辑制定，不得使用“数据库能打开”作为唯一验收标准。

#### D. 测试失败与恢复

至少增加：

- 每个历史版本连续升级至当前版本；
- 当前版本数据库重复启动；
- 缺列旧库的兼容性；
- migration 中途失败；
- migration 执行后再次启动；
- 高版本 schema 被旧版本客户端读取；
- 迁移后关键数据计数与内容对照。

失败测试使用临时数据库。不得用生产数据库模拟升级失败。

### 验收标准

- 所有真实历史版本均有可追踪的升级测试。
- 连续升级测试不跳过任何实际 migration。
- 核心业务数据在升级前后可对照。
- 迁移失败不会被错误记录为成功。
- 旧版本客户端不会自动降级更高版本数据库。
- `migration_ladder.rs` 及新增测试全部通过。
